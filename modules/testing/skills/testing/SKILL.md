# テスト

## テストの設計

[Test Desiderata](https://testdesiderata.com/) を基準に、対象に必要な性質を選ぶ。

- 独立性: 実行順に結果が依存しない。
- 合成可能性: 異なる変動要因を別々に検証し、結果を組み合わせられる。
- 決定性: 条件が変わらなければ結果も変わらない。
- 速さ: 短時間で実行できる。
- 書きやすさ: 対象コードに対して作成コストが見合う。
- 読みやすさ: テストを置く理由が読者に伝わる。
- 振る舞いへの感度: 対象の振る舞いが変わると結果も変わる。
- 構造への非依存: 構造だけの変更では結果が変わらない。
- 自動化: 人の介入なしに実行できる。
- 具体性: 失敗の原因が分かる。
- 予測性: 成功が本番での動作を予測する。
- 信頼: 成功が対象への信頼につながる。

これらは互いに補強する場合も、トレードオフになる場合もある。構成を工夫して両立できるかも検討する。

ソースを文字列として読んで未使用・構造・命名・配置を調べる検査は lint として扱い、アプリケーションの振る舞いを検証するテストと分ける。

ブラウザーのレンダリング・UI・E2E のテストはコストが高いので、業務の責務を説明できるものだけをテストする。色や配置のように、デザインの変更で変わる見た目のテストと、アクセシビリティーのテストは作らない。

## 作業中の確認

何を確かめれば次の判断に進めるかを先に決め、そのために必要な最小の範囲を実行する。使っているツールが持つ次の指定を選ぶ。

- ファイルやディレクトリーを渡して、変更に関係するテストだけを実行する。
- テスト名で絞る。
- 変更したファイルから import や依存をたどって、影響を受けるテストを選ぶ機能があれば使う。推測でテストファイルを選ぶより取りこぼしが少ない。渡すのはソースのファイルだけにする。依存の定義(package.json や lockfile)やツールの設定を渡すと、ツールによってはすべてのテストを選ぶ。設定を変えたときは、依存をたどらずに、その設定が効く検査を選ぶ。
- 失敗を直している間は、前回失敗したものだけを再実行する機能や、最初の失敗で止める指定を使う。
- 静的検査には、変更したファイルを渡す。
- 出力は、失敗の要点だけを出す形式や、出力を減らす指定で短くする。

あわせて、次のことを守る。

- カバレッジは push の前の検査で確かめ、作業中の確認では付けない。
- 検査スクリプトを通さずにツールを直接呼ぶときは、スクリプトが先に行う前処理(コード生成など)も実行する。
- 失敗したら、原因を切り分けられる範囲に絞って修正と再実行を繰り返す。範囲を広げるのは、影響をまだ確かめていない箇所が残るときにする。
- 多くのファイルから使われるファイルを変えると、依存をたどって選ぶテストが膨らみ、時間の上限に収まらないことがある。そのときは、変更したファイルを直接確かめるテストと、変えた振る舞いを確かめるテストに絞る。確かめなかった範囲は報告に書き、push の前の検査に任せる。
- 1 つの worker で直列に回す設定の検査が時間の上限に収まらないときは、shard の指定で分けて並行させる。並行させるのは、実行どうしがファイル・ポート・データベースを共有しない検査に限り、本数は同じマシン上のほかの実行を見て決める。
- 同じ検査をもう一度実行するのは、新しい変更か未解決の失敗があるときにする。

## push の前の検査

共有のブランチへ push する前に、統合する側が 1 回だけ行う。基準は CI が実行する必須の検査で、workflow と、それが呼ぶ script で確かめる。振る舞いの検証、静的検査、カバレッジの閾値は別々の条件として扱う。

### 通しで実行するとき

製品グレードのブランチや環境へ入る前は、必須の検査をすべて通しで実行する。製品グレードかどうかは、workflow のうち、push・マージ・タグで staging や production の環境へ配備するものの発火条件で見分ける。そのブランチへのマージや push、その環境へのデプロイがこれに当たる。

### 差分に関係する検査にするとき

それ以外の共有のブランチへ入る前は、取り込んだ差分に関係する検査にする。差分は、統合先の origin と、取り込んだあとの HEAD の間で取る。

- テストは、差分のファイルから依存をたどって影響を受けるものを選ぶ。渡すファイルの選び方は、作業中の確認と同じにする。依存をたどれないテスト(別のプロセスやブラウザー越しに動かすもの)は、差分が触れた機能を確かめるものだけを選ぶ。
- 型の検査、ビルド、依存の解決のように、プログラム全体を 1 つとして見る検査は、全体を実行する。
- lint のようにファイルごとに完結する静的検査は、差分のファイルに絞る。設定やルールを変えたときは全体にする。
- 入力に触れていない検査は飛ばす。workflow がファイルの変更で検査を走らせるかを決めている条件(paths など)があれば、それに合わせる。
- カバレッジの閾値のうち、ファイルごとに掛かるものは、差分のファイルについて確かめる。差分のファイルに依存するテストを、カバレッジの対象を差分のファイルに絞って実行する。そのファイルを通るテストは、そのファイルに依存するテストに含まれるので、通しの検査と同じ判定になる。全体や層の合計に掛かる閾値は差分では判定できないので、通しの検査に任せる。
  - CI は、ブランチによってテストやカバレッジを省いていることがある。ここで確かめなかった未達は、製品グレードへ入る前の通しの検査で初めて見つかり、積み上がった分を直すまでリリースが止まる。

### どちらにも共通すること

- 統合した組み合わせを確かめる。作業ブランチごとの確認は、作業中の確認で済んでいる。
- 重い検査を並行するときは、同じマシン上のほかの実行を考慮して本数を調整する。
- 完了の報告には、検証した対象、絞り方、満たした条件、実行していない必須検査を書く。
