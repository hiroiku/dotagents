# テスト

## テストの設計

[Test Desiderata](https://testdesiderata.com/) を基準に、対象に必要な性質を選ぶ。

- 独立性: 実行順に結果が依存しない。
- 合成可能性: 異なる変動要因を別々に検証し、結果を組み合わせられる。
- 決定性: 条件が変わらなければ結果も変わらない。
- 速さ: 短時間で実行できる。
- 書きやすさ: 対象コードに対して作成コストが見合う。
- 読みやすさ: テストを置く理由が読者に伝わる。
- 振る舞いへの感度: 対象の振る舞いが変わると結果も変わる。
- 構造への非依存: 構造だけの変更では結果が変わらない。
- 自動化: 人の介入なしに実行できる。
- 具体性: 失敗の原因が分かる。
- 予測性: 成功が本番での動作を予測する。
- 信頼: 成功が対象への信頼につながる。

これらは互いに補強する場合も、トレードオフになる場合もある。構成を工夫して両立できるかも検討する。

ソースを文字列として読んで未使用・構造・命名・配置を調べる検査は lint として扱い、アプリケーションの振る舞いを検証するテストと分ける。

## 作業中の確認

何を確かめれば次の判断に進めるかを先に決め、そのために必要な最小の範囲を実行する。プロジェクトが絞り方を定めていれば、それに従う。無ければ、使っているツールが持つ次の指定を選ぶ。

- ファイルやディレクトリーを渡して、変更に関係するテストだけを実行する。
- テスト名で絞る。
- 変更したファイルに依存するテストを選ぶ機能があれば使う。
- 失敗を直している間は、前回失敗したものだけを再実行する機能や、最初の失敗で止める指定を使う。
- コンパイルや型チェックは、増分で検査する指定を使う。
- 静的検査には、変更したファイルを渡す。
- 出力は、失敗の要点だけを出す形式や、出力を減らす指定で短くする。

あわせて、次のことを守る。

- カバレッジは仕上げの検査で確かめ、作業中の確認では付けない。
- 検査スクリプトを通さずにツールを直接呼ぶときは、スクリプトが先に行う前処理(コード生成など)も実行する。
- 失敗したら、原因を切り分けられる範囲に絞って修正と再実行を繰り返す。範囲を広げるのは、影響をまだ確かめていない箇所が残るときにする。
- 同じ検査をもう一度実行するのは、新しい変更か未解決の失敗があるときにする。

## 仕上げの検査

- 仕上げの検査では、プロジェクトが定める必須検査を実行する。振る舞いの検証、静的検査、カバレッジの閾値は別々の条件として扱う。
- 作業ブランチの検証と統合後の検証を分ける。統合後は、統合で変わった組み合わせを確かめる。
- 重い検査を並行するときは、同じマシン上のほかの実行を考慮して本数を調整する。
- 完了の報告には、検証した対象、満たした条件、実行していない必須検査を書く。
