## 検証

全体の検査は 1 回に数十秒から数十分かかり、作業中に繰り返すとセッションの大半がその待ち時間になる。一方で CI は手元より資源が少なく、実行ごとにお金もかかるので、CI で落ちないよう手元で確かめてから出す。手元で確かめるのは共有のブランチへ出す前の 1 回だけにし、どこまで確かめるかは入る先で決める。

- 作業中は、変更したファイルと、それに依存するテストだけを検査する。型の検査のようにファイルで絞れない検査は、増分で検査する指定で実行する。区切りを報告する前も同じで、それより広い検査はしない。絞り方は testing スキルを読む。
- 共有のブランチへ push する前に 1 回、統合する側が検査する。まとめて取り込んだ作業は、まとめて 1 回にする。作業ブランチを退避のために push するときは検査しない。
  - 製品グレードのブランチや環境(push やマージで staging や production へ配備されるもの。workflow で確かめる)へ入る前は、CI が実行する必須の検査を通しで実行する。
  - それ以外の共有のブランチへ入る前は、取り込んだ差分に関係する検査にする。テストは差分に依存するものだけ、型の検査やビルドのようにプログラム全体を見る検査は全体を回し、ファイルごとに掛かるカバレッジの閾値は差分のファイルについて確かめ、入力に触れていない検査は飛ばす。
- push の前の検査が失敗したら、失敗した検査だけに絞って直し、直した検査が通ったら push する。検査全体を実行し直すことはせず、CI に任せる。
- 一度実行した検査は、そのあとファイルを変更していなければ結果が変わらない。前回の結果をそのまま使う。
- 待つしかない処理は、時間の上限(ツールの timeout か、コマンド自身の待ち時間の指定)を付けてフォアグラウンドで実行する。バックグラウンドに回すのは待つあいだに進める作業があるときにし、結果は完了の通知で受け取る。
  - フォアグラウンドのコマンドが途中でバックグラウンドへ移されたら(Claude Code のサブエージェントでは 180 秒を超えると移されることがある)、その出力のファイルに終わりの印が出るまで待つ 1 つのコマンドを、175 秒以内の上限を付けて実行し、終わるまで繰り返す。出力を何度ものぞき直したり、決めた時間を待ったりしない。
  - 移されそうな長い検査で、成功すると何も出さないものは、`; echo "exit=$?"` のように終わりの印を出す形で実行する。
