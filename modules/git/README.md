# git

Git の操作に関わる共有ルール。[AGENTS.md](AGENTS.md) を常設ルールとして配り、コミットの主題、squash と rebase の選択、リリースのタグ、worktree の作り方と統合(統合先が保護されているときは PR の squash)、統合後の片付け、PR の扱いを定める。

これらはコミットや統合のたびに要り、どのセッションでも起きるので、スキルの呼び出しを待たずに読み込む。スキルとして配っていたころは、git の操作をしたセッションのうち読まれたのは 2 割前後で、読まれなかったセッションのコミットには AI の関与を示す行が残っていた。常設ルールはサブエージェントにも届く。

統合の流れは、作業ブランチを統合先から長く離さないことを軸にしている。作業する側は動く状態の区切りごとに、最新の統合先へ rebase してから報告し、報告にはブランチ、HEAD、検査の絞り方と結果、squash のタイトルの案を書く。統合する側は届いた報告をまとめて squash で取り込み、push の前の検査を 1 回で済ませる。この流れは urban-assault-2d のプロジェクト指示で使われて、うまく回っていたものを上げた。

squash で取り込んだブランチは `git branch --merged` で見分けられず、消し忘れが残りやすい。そこで、作業を終えたブランチは統合する側が、計測や試しのブランチは作った側が消す、と消す人と時を決めている。消す前には、報告された HEAD が取り込まれ、統合先が push 済みであることを確かめる。具体的な検査コマンド、ブランチ名、CI の発火条件は、対象プロジェクトの script と workflow を読んで確かめる。誰が worktree を用意し、誰がそこで作業するかの分担は `collaboration` モジュールが持つ。

AI の関与を示す記述(署名の行とセッションの URL)は、規則を読んでいてもハーネスの促しで混じることがある。そこで `hooks/no-ai-attribution.mjs` が、コミット、PR、issue を書く git と gh の呼び出しを見て、混じっていれば実行の前に止める。本文をファイルで渡す指定(`-F`、`--body-file`、`body=@`)は、ファイルの中身も読む。Claude Code と Codex の両方で動く。
