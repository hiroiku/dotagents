## Git

- コミットタイトルには、業務にとって何が変わったかを書く。ファイル名や内部の識別子を主題にしない。
- コミットメッセージと PR に、Co-Authored-By や Generated with など AI の関与を示す記述を入れない。
- 統合は squash を既定とする。upstream への追従は merge ではなく rebase を使う。
- リリースやデプロイを指示されたら、バージョンを上げてタグを付ける。

### worktree と統合

並行する作業は同じ土台を触るので、作業ブランチが統合先から離れるほど統合の手戻りが増える。小さい区切りで統合し、こまめに追従する。

- 作業ブランチは、作業ごとに worktree として作る。
- 作業する側は、動く状態で区切りがつくたびに報告する。区切りを溜めて大きな統合にしない。報告の前に最新の統合先へ rebase する。
- 報告には、ブランチ、HEAD のコミット、何に絞って何を検査し何が通ったか、squash のコミットタイトルの案を書く。
- 統合先が進み、触るファイルや前提にしている土台が変わったら、区切りで最新の統合先へ rebase して追従する。
- 統合は統合先ブランチの worktree で行う。共有ブランチで `git reset` を使わない。
- 統合する側は、届いている報告のブランチをまとめて squash で取り込み、取り込んだ組み合わせを push の前の検査で確かめてから push する。作業ブランチの変更による失敗なら、push せずに作業する側へ戻す。
- 統合先が保護されていて PR でしか取り込めないときは、統合先の worktree での取り込みと push に代えて PR の squash で統合する。統合先の worktree では取り込まず、origin から取ってくるだけにする。

### 片付け

- 作業が終わり、最後の区切りを取り込んで push したら、統合する側がその worktree とブランチをローカルとリモートから消す。
- 計測や試しのために作った worktree とブランチは、作った側が目的を終えた時点で消す。
- 消す前に、報告された HEAD の変更が統合先へ取り込まれ、統合先が origin へ push 済みであることを確かめる。squash で取り込んだブランチは `git branch --merged` では見分けられない。

### PR と CI

- PR は draft で開き、変更と検証が完了した時点で ready にする。
- PR や push で何が実行されるかは、対象リポジトリーの workflow で確かめる。draft の PR でも CI が走ることがある。
