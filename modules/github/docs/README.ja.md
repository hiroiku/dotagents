GitHub の issue が何を担えるのか、どの意味をどの仕組みが担うのかについての module。規約そのものは [skills/issues/SKILL.md](../skills/issues/SKILL.md) にある。

## 何もかもが label になる

label は、どのモデルも既に知っている唯一の仕組みである。だから他所に属する物を吸い込む — 作業の種類、狙っているリリース、大きな仕事のどの部分か、何を待っているか。エラーにはならない。issue は立ち、色が付き、整理されて見える。

失われるのは問いである。リリースを label で書けば、`is:open no:milestone` はリリース未定の作業を見つけられない。子を本文の散文で触れただけなら、親の進捗は数えられない。**tracker は一度書かれ、何百回も読まれる**。誤った軸に置かれた意味は、以後のすべての読み取りから差し引かれる。

だからこのスキルは `gh issue` の案内ではない。意味から軸への地図であり、短い。残りは `--help` にある。

## モデルが導けないこと

`gh issue create --help` はいつでも読める。そこから得られないのは:

| | |
| --- | --- |
| 関係は今やネイティブ | `--parent`・`--add-sub-issue`・`--add-blocked-by` は最近 `gh` に入った。古い `gh` で学んだモデルはコミュニティの拡張や手書きの GraphQL に手を伸ばし、既に組み込まれている物の劣った版を得る。 |
| 穴は milestone | 他の軸はすべてフラグだが、milestone 自体だけが REST である。穴の位置を正確に知っていれば、両方の誤りを防げる — 割り当てに API を呼ぼうとすることと、存在しない `gh milestone` を探すこと。 |
| type は label ではない | issue type は組織に対して定義され、すべてのリポジトリが同じ集合から引く。新しく、見落としやすく、そして `bug` という label が普通は要らない理由である。 |
| sub-issue はチェックボックスではない | 本文のタスクリストは見た目が同じで、状態を持たない。何も問い合わせられず、親から数えることもできない。 |

## 判断が分かれたところ

**label 名の規約を置かない。** あるチームの流れに合う体系は次のチームには誤りであり、誰も守らない規則は、何も買わずに注意力だけを費やす。この module が縛るのは意味がどの軸に属するかであって、その軸にどんな label が並ぶかはチームの物である。

**本文のテンプレートを置かない。** 良い報告に何が要るかは判断であり、有能なモデルは既に持っている。述べる価値のある機械的な事実は 1 つ — 本文は stdin から渡す。シェルの引用符が markdown を壊すからだ。それだけ述べて、あとは触らない。

**issue ではなくホストの名を採る。** pull request も release も Actions も同じプラットフォームの上にあり、問題の形も同じである。module 名を `github` にしてあるので、次のスキルには降りる場所がある。
