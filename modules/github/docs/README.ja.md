GitHub の issue が何を担えるのか、どの意味をどの仕組みが担うのかについての module。規約そのものは [skills/issues/SKILL.md](../skills/issues/SKILL.md) にある。

## 何もかもが label になる

label は、どのモデルも既に知っている唯一の仕組みである。だから他所に属する物を吸い込む — 作業の種類、狙っているリリース、大きな仕事のどの部分か、何を待っているか。エラーにはならない。issue は立ち、色が付き、整理されて見える。

失われるのは問いである。リリースを label で書けば、`is:open no:milestone` はリリース未定の作業を見つけられない。子を本文の散文で触れただけなら、親の進捗は数えられない。**tracker は一度書かれ、何百回も読まれる**。誤った軸に置かれた意味は、以後のすべての読み取りから差し引かれる。

だからこのスキルは `gh issue` の案内ではない。それぞれの機能が何を買うのか — どの問いを後で答えられるようにするのか — についてである。機能に手を伸ばす理由は、それしかない。

## 答えられるか、答えられないか

その機能を使った甲斐があったかを分ける線:

| | |
| --- | --- |
| チェックボックスは sub-issue ではない | 見た目は同じである。一方は独自の状態を持ち親から数えられるオブジェクトで、他方はただの文字列である。分解の見返りは丸ごとこの線の片側にある。 |
| blocking は絞り込みに使えない | 他の軸はどれも一覧を狭めるが、これだけは狭めない。順序を tracker に記す価値はあるが、誰かが手で待ち行列を組み立てる場合に限られる。 |
| 閉じられない milestone は何も答えない | バーンダウンも「間に合うのか」の読みも、日付で終わる集合から出てくる。`backlog` や `someday` はどちらも生まず、そこに抱えた物すべての読みを静かに奪う。 |
| type はリポジトリを跨ぎ、label は跨がない | type は組織の物なので、1 つの問いが全リポジトリを一度に横断できる。両方 `bug` という名の label は、互いについて何も保証しない。 |

## 判断が分かれたところ

**label 名の規約を置かない。** あるチームの流れに合う体系は次のチームには誤りであり、誰も守らない規則は、何も買わずに注意力だけを費やす。この module が縛るのは意味がどの軸に属するかであって、その軸にどんな label が並ぶかはチームの物である。

**本文のテンプレートを置かない。** 良い報告に何が要るかは判断であり、有能なモデルは既に持っている。この module が決めるのは意味の行き先であって、言葉遣いではない。

**issue ではなくホストの名を採る。** pull request も release も Actions も同じプラットフォームの上にあり、問題の形も同じである。module 名を `github` にしてあるので、次のスキルには降りる場所がある。
