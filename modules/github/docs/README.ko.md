GitHub의 issue가 무엇을 담을 수 있는지, 어떤 의미를 어떤 장치가 담는지에 관한 module. 규약 자체는 [skills/issues/SKILL.md](../skills/issues/SKILL.md)에 있다.

## 무엇이든 label이 된다

label은 어떤 모델이든 이미 알고 있는 유일한 장치다. 그래서 다른 데 속한 것까지 빨아들인다 — 작업의 종류, 겨냥한 릴리스, 더 큰 일의 어느 조각인지, 무엇을 기다리는지. 오류는 나지 않는다. issue는 세워졌고, 색이 붙었고, 정리된 것처럼 보인다.

잃는 것은 질문이다. 릴리스를 label로 적으면 `is:open no:milestone`은 릴리스가 정해지지 않은 일을 찾아내지 못한다. 자식을 본문에 문장으로만 적어 두면 부모의 진척은 셀 수 없다. **tracker는 한 번 쓰이고 수백 번 읽힌다.** 잘못된 축에 놓인 의미는 이후의 모든 읽기에서 빠진다.

그래서 이 skill은 `gh issue`의 안내가 아니다. 각 기능이 무엇을 사는지 — 어떤 물음을 나중에 답할 수 있게 하는지 — 에 관한 것이다. 기능에 손을 뻗을 이유는 그것뿐이다.

## 답할 수 있는가, 없는가

그 기능을 쓴 보람이 있었는지를 가르는 선:

| | |
| --- | --- |
| 체크박스는 sub-issue가 아니다 | 겉모습은 같다. 하나는 제 상태를 갖고 부모가 셀 수 있는 객체이고, 다른 하나는 그냥 글자다. 분해의 대가는 통째로 이 선의 한쪽에 있다. |
| blocking은 걸러낼 수 없다 | 다른 축은 모두 목록을 좁히지만 이것만은 좁히지 못한다. 순서를 tracker에 남길 값어치는 있지만, 누군가 손으로 대기열을 짜 맞출 때에 한한다. |
| 닫힐 수 없는 milestone은 아무것도 답하지 않는다 | 번다운도 "제때 되겠는가"라는 읽기도, 날짜로 끝나는 집합에서 나온다. `backlog`나 `someday`는 둘 다 만들지 못하고, 그 안에 담긴 모든 것의 읽기를 조용히 앗아간다. |
| type은 저장소를 가로지르고 label은 그러지 못한다 | type은 조직의 것이라 하나의 물음이 모든 저장소를 한 번에 가로지른다. 둘 다 `bug`라는 이름의 label은 서로에 대해 아무것도 보장하지 않는다. |

## 판단이 갈린 자리

**label 이름 규약을 두지 않는다.** 한 팀의 흐름에 맞는 체계는 다음 팀에게는 틀리고, 아무도 지키지 않는 규칙은 아무것도 사지 못한 채 주의력만 쓴다. 이 module이 묶는 것은 의미가 어느 축에 속하는가이며, 그 축에 어떤 label이 늘어서는지는 팀의 몫이다.

**본문 템플릿을 두지 않는다.** 좋은 보고에 무엇이 필요한지는 판단이고, 유능한 모델은 이미 갖고 있다. 이 module이 정하는 것은 의미가 갈 자리이지, 문장을 어떻게 쓰는가가 아니다.

**issue가 아니라 호스트의 이름을 딴다.** pull request도 release도 Actions도 같은 플랫폼 위에 있고, 문제의 형태도 같다. module 이름이 `github`인 덕에 다음 skill에는 내려앉을 자리가 있다.
