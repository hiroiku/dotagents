GitHub의 issue가 무엇을 담을 수 있는지, 어떤 의미를 어떤 장치가 담는지에 관한 module. 규약 자체는 [skills/issues/SKILL.md](../skills/issues/SKILL.md)에 있다.

## 무엇이든 label이 된다

label은 어떤 모델이든 이미 알고 있는 유일한 장치다. 그래서 다른 데 속한 것까지 빨아들인다 — 작업의 종류, 겨냥한 릴리스, 더 큰 일의 어느 조각인지, 무엇을 기다리는지. 오류는 나지 않는다. issue는 세워졌고, 색이 붙었고, 정리된 것처럼 보인다.

잃는 것은 질문이다. 릴리스를 label로 적으면 `is:open no:milestone`은 릴리스가 정해지지 않은 일을 찾아내지 못한다. 자식을 본문에 문장으로만 적어 두면 부모의 진척은 셀 수 없다. **tracker는 한 번 쓰이고 수백 번 읽힌다.** 잘못된 축에 놓인 의미는 이후의 모든 읽기에서 빠진다.

그래서 이 skill은 `gh issue`의 안내가 아니다. 의미에서 축으로 가는 지도이며, 짧다. 나머지는 `--help`에 있다.

## 모델이 도출할 수 없는 것

`gh issue create --help`는 언제든 읽을 수 있다. 거기서 얻을 수 없는 것은:

| | |
| --- | --- |
| 관계는 이제 네이티브다 | `--parent`, `--add-sub-issue`, `--add-blocked-by`는 최근에야 `gh`에 들어왔다. 옛 `gh`로 배운 모델은 커뮤니티 확장이나 손으로 쓴 GraphQL로 손을 뻗고, 이미 내장된 것의 열등한 판본을 얻는다. |
| 구멍은 milestone | 다른 축은 모두 플래그인데, milestone 자체만 REST다. 구멍의 위치를 정확히 알면 양쪽 실수를 모두 막는다 — 배정에 API 호출을 지어내는 일과, 존재하지 않는 `gh milestone`을 찾아 헤매는 일. |
| type은 label이 아니다 | issue type은 조직 단위로 정의되고 모든 저장소가 같은 집합에서 가져다 쓴다. 새롭고, 놓치기 쉽고, `bug`라는 label이 대개 필요 없는 이유이기도 하다. |
| sub-issue는 체크박스가 아니다 | 본문의 작업 목록은 겉모습이 같지만 상태를 갖지 않는다. 무엇도 질의할 수 없고, 부모에서 셀 수도 없다. |

## 판단이 갈린 자리

**label 이름 규약을 두지 않는다.** 한 팀의 흐름에 맞는 체계는 다음 팀에게는 틀리고, 아무도 지키지 않는 규칙은 아무것도 사지 못한 채 주의력만 쓴다. 이 module이 묶는 것은 의미가 어느 축에 속하는가이며, 그 축에 어떤 label이 늘어서는지는 팀의 몫이다.

**본문 템플릿을 두지 않는다.** 좋은 보고에 무엇이 필요한지는 판단이고, 유능한 모델은 이미 갖고 있다. 적어 둘 값어치가 있는 기계적 사실은 하나뿐이다 — 본문은 stdin으로 넘긴다. 셸의 따옴표가 markdown을 망가뜨리기 때문이다. 거기까지만 말하고 나머지는 건드리지 않는다.

**issue가 아니라 호스트의 이름을 딴다.** pull request도 release도 Actions도 같은 플랫폼 위에 있고, 문제의 형태도 같다. module 이름이 `github`인 덕에 다음 skill에는 내려앉을 자리가 있다.
