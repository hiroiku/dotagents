## レビュー

実装や修正を終えたら、完了を報告する前に、該当するレビューエージェントに検証を任せる。依頼に書く実行方法は、要件を満たしていないことを示せるテストや操作に絞ったコマンドにする。

- レビューは、実装した worktree で、報告された HEAD のコミットに対して行う。レビューのために worktree やブランチを作らない。レビューのあいだ、実装する側はその worktree を変更しない。
- ファイルを一時的に書き換えて確かめること(壊して落ちるかを見る、変更前のコードに戻して比べる)は、その worktree で動くレビュアーが 1 体だけのときに、依頼に書いて許す。並行するレビュアーがいるときに書き換えると、ほかのレビュアーの実行が書き換えた状態を読む。
- レビューから戻ったら、HEAD がレビューの前と同じで、コミットしていない変更が無いことを確かめる。
- 直すのは、要件の未達と、この変更が壊したもののうち、起きる条件と再現が示された指摘にする。レビュアーが付けた重さの言葉では決めない。重さの付け方はレビュアーによって揺れ、要件の未達が「低」とされることもある。
- 変更前からある不具合は直さずに issue の候補として報告に載せる。要件が 2 通りに読めるという指摘は、実装に直させずに、依頼元(対話を担当するセッションならユーザー)に確かめる。
- 指摘の修正は、実装したエージェントに続けて依頼する。直す前に指摘の再現を落ちるテストとして書き、直したら、そのテストと要件を確かめるテストが通ってから再レビューに出すよう伝える。直しが持ち込む不具合は多くが別の要件の未達で、要件のテストが通っていればレビューに届く前に止まる。
  - コントラストや画面の幅ごとの配置のように、描画しないと分からない指摘はテストにしない。レビュアーが示した再現の手順で直ったことを確かめてから再レビューに出すよう伝える。
- 再レビューは、同じレビュアーに続けて依頼し(Claude Code では SendMessage)、修正のコミットを渡して、その指摘が解消されたかと修正の差分だけを確かめてもらう。新しいレビュアーは前回の指摘を知らずに初めから読み直し、新しい指摘を出し続けるので、往復が終わらない。
- 再レビューで、直しが新しい不具合を持ち込んだか、同じ指摘が直しのあとも残ったと分かったら、続けて継ぎ足さない。実装したエージェントに、その部分の作り方を見直すよう依頼し、要件や設計を変えるときは依頼元(対話を担当するセッションならユーザー)に確かめる。直すたびに仕組みを足して新しい不具合が出るのは、作り方が要件に合っていないことが多い。
- 同じ種類の指摘が別の作業でも続けて出たら、作業ごとに直し続けない。原因を 1 か所で直す方法(共通の部品、プロジェクトの決まり、依頼に書く要件)を、依頼元(対話を担当するセッションならユーザー)に提案する。作業ごとに直すだけでは、次の作業でも同じ指摘をレビューが見つけ直すことになる。
