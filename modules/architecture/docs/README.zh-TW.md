一個以機器可檢查的形式,決定依賴方向、檔案歸屬、命名與失敗傳遞方式的 module。規約本身在 [skills/design/SKILL.md](../skills/design/SKILL.md)。

## 讀不完的東西,憑什麼信任

AI 產出的變更量已經超過人能讀完的量。審查從逐行縮為抽樣,很多時候只剩下「還能跑嗎」的確認。也就是說,人不再確認 **HOW(怎麼寫的),而是開始信任 WHAT(做出了什麼)**。

這份信任是否成立,不取決於閱讀者的耐力,而取決於 **HOW 是否被機制約束住**。沒被讀到的那部分裡潛藏著什麼都好:只要形狀上寫不出來,它就不在那裡。

這裡有一重矛盾。嚴格的規約,過去的上限是「人能守住多少」。寫不了超過能記住的量,是否被遵守只能靠眼睛確認,於是規約越多越守不住。嚴格是理想,但代價太高——這是人類時代的行情。

當書寫者變成 AI,這個行情就變了。寫樣板程式碼的成本幾乎消失。而對 AI 而言昂貴的是**猜測該放在哪裡**,需要猜測的結構會直接抬高放錯位置的機率。嚴格變便宜了,含糊變貴了。行情反轉了。

但約束過頭就會扼殺模型的判斷力。所以這套規約只約束**結構**,不約束**判斷**。層固定為 6 個,層內的 `<kind>` 不固定。邊界由規約定下,邊界之內解決什麼、怎麼解決,交給書寫者。

## 不是「發現得了」,而是「寫不出來」

規則的大部分,都從審查需要**發現**的位置,挪到了一開始就**寫不出來**的位置。

| 要守住的東西         | 由什麼來守                             |
| -------------------- | -------------------------------------- |
| 跨層的依賴           | 建置設定(看不見的層無法通過型別解析) |
| 技術詞彙滲入內側     | 根本沒有可 import 的外部套件           |
| 沒有對應埠的配接器   | 檔名規則                               |
| 合成時的註冊遺漏     | 型別                                   |
| 失敗被吞掉           | `Result` 的回傳型別                    |
| 繞開依賴圖           | 不把容器交出去                         |

這不是靠審查找出違規的設計,而是**寫下的那一刻就失敗**的設計。在沒人會讀完全部的前提下,這個差別就是安心的量。

位置唯一、名字即說明角色,同樣服務於這個目的:它既是人的可讀性,也是 AI 更低的檢索成本。

## 借了什麼,沒借什麼

| 約定                                         | 出處                       |
| -------------------------------------------- | -------------------------- |
| 依賴永遠指向內側                             | Clean Architecture         |
| 配接器二分為 driving / driven                | 埠與配接器(六邊形)       |
| `<bounded_context>` 這一軸、內側只用業務語言 | DDD                        |
| 合成的根只有一個                             | DI 的 composition root     |
| 失敗作為值回傳,`throw` 僅限於 bug            | 函數式的錯誤處理           |
| 按層的建置設定把違規變成編譯錯誤             | 本 module 獨有             |
| 測試是層的鏡像,鏡像同樣受依賴規則約束       | 本 module 獨有             |

**這不是 Clean Architecture 的實作。** 作為不變式採納的只有依賴規則,那張圖並未照搬。尤其是輸出埠(presenter 實作 application 側埠的形態)沒有採用。

**這也不是 DDD 的實作。** 借來的只有 bounded context 與 ubiquitous language 兩項,聚合與戰略設計的其餘部分並未帶入。

**層是內外,不是上下。** 與自上而下流動的經典分層不同,依賴永遠朝內,外側不為內側所知。

## 判斷可能分歧之處

規約中本可以有別的選法之處,以及選擇的理由。

**`interface` 不看 `domain`。** controller 一旦碰到 entity,領域的形狀就會滲進接線的形狀。重構領域會開始破壞對外的契約,CA 想要防住的東西又回來了。代價是 use-case 要持有自己的輸入輸出型別、presenter 要寫轉換,但那個轉換正是邊界的翻譯。

**`frameworks` 不看 `application`。** 入口有兩條時,放在 controller 裡的橫切處理(認證、驗證、錯誤翻譯)會在另一條路徑上**悄無聲息地漏掉**。不會報錯,只是通過了。這是最危險的壞法,所以入口保持一條。

**不使用輸出埠。** use-case 驅動 presenter 的經典形態,回傳值是 `void`,於是**呼叫方忽略結果時編譯器也保持沉默**。回傳 `Result` 的形態,不同時處理成功與失敗就通不過型別檢查。這裡選了型別的強度。

**保留 `ports/` 這一層。** 把埠放在與其他種類相同的高度,「從外部需要的東西的宣告」與「自身的邏輯」就無法憑名字區分。付出一級的不對稱,換來這個區分是看得見的。

**配接器冠以埠之名。** 相對於 `storage.integration.ts` 的 `google-drive-storage.integration.ts`。滿足哪個埠從名字就能讀出,沒有對應埠的孤兒可以用機器篩掉。

**容器不跨越邊界。** 內側一旦能接過 resolver,不 import 也能取出任何東西。**import 圖不再講述真實的依賴**,建置設定與 linter 都會失效。依賴用參數傳。

**合成放在各層級,根只有一個。** 把接線放在程式碼旁邊,增加一個 use-case 時只需動隔壁的一個檔案。層的合成只看自己的層,所以不會破壞層的規則。跨層的只有根,例外止於此。

## 適合與不適合

適合長壽命、外部服務有多個、AI 大量參與的程式庫。一次性的東西,或外部依賴只有一個的小東西,不值得付出這份手續費。
