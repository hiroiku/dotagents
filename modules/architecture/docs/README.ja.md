依存の向き・置き場所・名前・失敗の扱いを、機械が検査できる形で決める module。規約そのものは [skills/design/SKILL.md](../skills/design/SKILL.md) にある。

## 読み切れないものを、どう信じるか

AI が出す変更は、人が読み切れる量を超えた。レビューは全数から標本へ縮み、多くの場面では「動いたか」の確認になる。つまり人は **HOW(どう書いたか)を確かめないまま、WHAT(何ができたか)を信じる**ことになる。

信じてよいかどうかは、読む側の根気ではなく、**HOW が仕組みで縛られているか**で決まる。読まなかった部分に何が潜んでいようと、書けない形になっているなら、そこには無い。

ここに葛藤がある。厳密な規約は、これまで「人が守れる量」が上限だった。覚えられる以上のことは書けず、守られたかは目で確かめるしかなく、だから規約は増えるほど守られなくなる。厳密さは理想だが高くつく、というのが人間の時代の相場だった。

書き手が AI になると、その相場が変わる。定型を書く手間はほぼ消える。一方で、**置き場所を推測するコスト**は AI にとって高い。推測が要る構造は、間違った場所に置かれる確率をそのまま上げる。厳密さの支払いは軽くなり、曖昧さの支払いは重くなった。逆転している。

とはいえ縛りすぎれば、モデルの判断力を殺す。だからこの規約が縛るのは**構造**だけで、**判断**は縛らない。層は 6 つに固定するが、その中の `<kind>` は固定しない。境界は決めるが、境界の中で何をどう解くかは書き手に委ねる。

## 気づくのではなく、書けないようにする

規則のほとんどは、レビューで**気づく**ものではなく、はじめから**書けない**ものへ寄せてある。

| 守りたいこと               | 何が守るか                               |
| -------------------------- | ---------------------------------------- |
| 層をまたぐ依存             | ビルド構成(見えない層は型解決に失敗する) |
| 内側に技術語彙が入ること   | 外部パッケージを import できないこと自体 |
| ポートに対応しないアダプタ | ファイル名の規則                         |
| 合成の登録漏れ             | 型                                       |
| 失敗の握り潰し             | `Result` の戻り値型                      |
| 依存の迂回                 | コンテナを渡さないこと                   |

レビューで見つける設計ではなく、**書いた時点で落ちる**設計である。人が全部を読まなくなる前提では、この差がそのまま安心の量になる。

置き場所が一意で、名前から役割が読めることも、同じ目的に効く。人間の可読性であると同時に、AI の探索コストの低さでもある。

## 何を借り、何を借りていないか

| 取り決め                                         | 出自                           |
| ------------------------------------------------ | ------------------------------ |
| 依存は常に内側を向く                             | Clean Architecture             |
| アダプタを driving / driven に二分する           | ポートとアダプタ(ヘキサゴナル) |
| `<bounded_context>` の軸、内側は業務の言葉だけ   | DDD                            |
| 合成の根はひとつ                                 | DI の composition root         |
| 失敗は値として返し、`throw` はバグに限る         | 関数型のエラー処理             |
| 層ごとのビルド構成で違反をコンパイルエラーにする | この module 独自               |
| テストを層の鏡像にし、鏡像にも依存規則を掛ける   | この module 独自               |

**これは Clean Architecture の実装ではない。** 不変条件として採ったのは依存規則だけで、図はそのまま写していない。とくに出力ポート(presenter が application 側のポートを実装する形)は使わない。

**これは DDD の実装でもない。** 借りているのは bounded context と ubiquitous language の 2 つだけで、集約や戦略的設計の全体を持ち込んではいない。

**層(layer)は上下ではなく内外である。** 上から下へ流れる古典的なレイヤードとは違い、依存は常に内向きで、外側は内側に知られない。

## 判断が分かれたところ

規約の中で、他の選び方もありえた箇所と、選んだ理由。

**`interface` は `domain` を見ない。** controller が entity に触れると、ドメインの形が配線の形に漏れる。ドメインのリファクタが外部への契約を壊すようになり、CA が防ごうとしたものが戻ってくる。代償は use-case が入出力の型を持ち、presenter が変換を書くことだが、その変換こそが境界の翻訳である。

**`frameworks` は `application` を見ない。** 入口が 2 本あると、controller に置いた横断的な処理(認証・検証・エラー翻訳)が、もう一方の経路で**黙って抜け落ちる**。エラーにならず、ただ通る。これが最も危ない壊れ方なので、入口を 1 本に保つ。

**出力ポートを使わない。** use-case が presenter を駆動する古典形は、戻り値が `void` になるため**呼び手が結果を無視してもコンパイラが黙る**。`Result` を返す形なら、成功と失敗の両方を扱わない限り型が通らない。型の強さを取った。

**`ports/` を一段残す。** ポートを他の種類と同じ高さに置くと、「外から要る物の宣言」と「自分の論理」が名前から区別できなくなる。一段の非対称を払って、区別を目に見えるようにしている。

**アダプタはポート名を冠する。** `storage.integration.ts` に対する `google-drive-storage.integration.ts`。どのポートを満たす実装かが名前で読め、対応するポートの無い孤児を機械で落とせる。

**コンテナは境界を越えない。** 内側が resolver を受け取れると、import せずに何でも取り出せる。**import グラフが実際の依存を語らなくなり**、ビルド構成もリンタも無力になる。依存は引数で渡す。

**合成は各階層に置き、根だけがひとつ。** 配線をコードの隣に置くと、use-case を足すときに触るのは隣の 1 ファイルで済む。層の合成は自分の層しか見ないので、層の規則を破らない。層をまたぐのは根だけであり、例外はそこに限られる。

## 向き・不向き

長命で、外部サービスが複数あり、AI が大量に触るコードベースに向く。使い捨ての物や、外部依存がひとつしかない小さな物には、払う手間に見合わない。
