## 다 읽을 수 없는 것을, 어떻게 믿을 것인가

AI가 내놓는 변경의 양은 사람이 다 읽을 수 있는 양을 넘어섰다. 리뷰는 전수에서 표본으로 줄고, 많은 경우 "돌아가는가"의 확인이 된다. 즉 사람은 **HOW(어떻게 썼는가)를 확인하지 않은 채 WHAT(무엇이 되었는가)을 믿게** 된다.

그 믿음이 정당한지는 읽는 쪽의 끈기가 아니라, **HOW가 장치로 묶여 있는가**가 정한다. 읽지 않은 부분에 무엇이 숨어 있든, 애초에 쓸 수 없는 형태라면 거기에 없다.

여기에 갈등이 있다. 엄밀한 규약의 상한은 지금까지 "사람이 지킬 수 있는 양"이었다. 기억할 수 있는 이상은 쓸 수 없고, 지켜졌는지는 눈으로 확인할 수밖에 없어서, 규약은 늘어날수록 지켜지지 않았다. 엄밀함은 이상이지만 비싸다 — 그것이 인간의 시대의 시세였다.

쓰는 쪽이 AI가 되면 그 시세가 바뀐다. 정형을 쓰는 수고는 거의 사라진다. 반면 AI에게 비싼 것은 **어디에 두어야 할지 추측하는 비용**이며, 추측이 필요한 구조는 잘못된 자리에 놓일 확률을 그대로 올린다. 엄밀함의 값은 싸지고, 모호함의 값은 비싸졌다. 뒤집힌 것이다.

그렇다고 지나치게 묶으면 모델의 판단력을 죽인다. 그래서 이 규약이 묶는 것은 **구조**뿐이며 **판단**은 묶지 않는다. 층은 6개로 고정하지만 그 안의 `<kind>`는 고정하지 않는다. 경계는 정하되, 경계 안에서 무엇을 어떻게 풀지는 쓰는 사람에게 맡긴다.

## "알아채기"가 아니라 "쓸 수 없게"

규칙의 대부분은 리뷰에서 **알아채야 하는** 자리가 아니라, 처음부터 **쓸 수 없는** 자리로 옮겨 두었다.

| 지키고 싶은 것            | 무엇이 지키는가                            |
| ------------------------- | ------------------------------------------ |
| 층을 넘는 의존            | 빌드 구성(보이지 않는 층은 타입 해석에 실패한다) |
| 안쪽에 기술 어휘가 들어옴 | import할 외부 패키지가 없다는 사실 자체    |
| 포트에 대응하지 않는 어댑터 | 파일명 규칙                              |
| 합성에서의 등록 누락      | 타입                                       |
| 실패의 묵살               | `Result` 반환 타입                         |
| 의존의 우회               | 컨테이너를 건네지 않는 것                  |

리뷰에서 찾아내는 설계가 아니라 **쓰는 순간 떨어지는** 설계다. 사람이 전부를 읽지 않게 된 전제에서는, 그 차이가 곧 안심의 양이다.

놓일 자리가 하나뿐이고 이름에서 역할이 읽히는 것도 같은 목적에 듣는다. 사람의 가독성인 동시에 AI의 낮은 탐색 비용이다.

## 무엇을 빌리고, 무엇을 빌리지 않았는가

| 규정                                              | 출처                       |
| ------------------------------------------------- | -------------------------- |
| 의존은 언제나 안쪽을 향한다                       | Clean Architecture         |
| 어댑터를 driving / driven으로 나눈다              | 포트와 어댑터(헥사고날)    |
| `<bounded_context>` 축, 안쪽은 업무의 말만        | DDD                        |
| 합성의 뿌리는 하나                                | DI의 composition root      |
| 실패는 값으로 반환하고 `throw`는 버그에 한한다    | 함수형의 에러 처리         |
| 층별 빌드 구성으로 위반을 컴파일 에러로 만든다    | 이 module 고유             |
| 테스트를 층의 거울상으로 두고 거울상에도 규칙 적용 | 이 module 고유            |

**이것은 Clean Architecture의 구현이 아니다.** 불변식으로 취한 것은 의존 규칙뿐이며, 그림을 그대로 옮기지는 않았다. 특히 출력 포트(presenter가 application 쪽 포트를 구현하는 형태)는 쓰지 않는다.

**DDD의 구현도 아니다.** 빌린 것은 bounded context와 ubiquitous language 두 가지뿐이며, 애그리게이트나 전략적 설계의 전체를 들여오지는 않았다.

**층은 위아래가 아니라 안팎이다.** 위에서 아래로 흐르는 고전적 레이어드와 달리, 의존은 언제나 안쪽을 향하고 바깥은 안쪽에 알려지지 않는다.

## 판단이 갈린 자리

규약 중 다른 선택도 가능했던 곳과, 그것을 고른 이유.

**`app-kernel`은 공유 커널이 아니다.** DDD의 shared kernel은 두 context가 함께 갖기로 합의한 도메인이지만, 이것은 그것이 아니다. 여기에 사는 것은 아키텍처 자체가 돌아가기 위한 기구(`Result`, 에러의 기저 타입)이며, 이 제품이 무엇을 하는지 때문에 존재하는 것은 하나도 없다. 모두가 import해도 되는 유일한 잎이라는 점이 공유하고 싶은 것의 가장 값싼 자리로 만들어 버린다 — 그래서 제품 고유의 개념이 가장 먼저 고이는 층이고, 무엇을 담지 않는지로 정의할 수밖에 없는 층이다. 업무의 안쪽은 `domain`이다. `app-kernel`은 그림 전체의 아래에 있다.

**`interface`는 `domain`을 보지 않는다.** controller가 entity에 손대면 도메인의 형태가 배선의 형태로 샌다. 도메인 리팩터링이 외부와의 계약을 깨기 시작하고, CA가 막으려던 것이 돌아온다. 대가는 use-case가 입출력 타입을 갖고 presenter가 변환을 쓰는 일이지만, 그 변환이야말로 경계의 번역이다.

**`frameworks`는 `application`을 보지 않는다.** 입구가 둘이면 controller에 둔 횡단 처리(인증·검증·에러 번역)가 다른 경로에서 **조용히 빠진다**. 에러가 나지 않고 그냥 통과한다. 가장 위험한 고장 방식이므로 입구를 하나로 유지한다.

**출력 포트를 쓰지 않는다.** use-case가 presenter를 구동하는 고전형은 반환값이 `void`가 되어 **호출자가 결과를 무시해도 컴파일러가 침묵한다**. `Result`를 반환하는 형태라면 성공과 실패를 모두 다루지 않는 한 타입이 통과하지 않는다. 타입의 강함을 택했다.

**`ports/`를 한 단 남긴다.** 포트를 다른 종류와 같은 높이에 두면 "밖에서 필요한 것의 선언"과 "자신의 논리"를 이름으로 구분할 수 없게 된다. 한 단의 비대칭을 치르고 그 구분을 눈에 보이게 했다.

**어댑터는 포트 이름을 앞에 쓴다.** `storage.integration.ts`에 대한 `google-drive-storage.integration.ts`. 어느 포트를 만족하는 구현인지 이름에서 읽히고, 대응하는 포트가 없는 고아를 기계로 떨굴 수 있다.

**컨테이너는 경계를 넘지 않는다.** 안쪽이 resolver를 받을 수 있으면 import하지 않고도 무엇이든 꺼낼 수 있다. **import 그래프가 실제 의존을 말하지 않게 되고**, 빌드 구성도 린터도 무력해진다. 의존은 인자로 건넨다.

**합성은 각 계층에 두고, 뿌리만 하나.** 배선을 코드 옆에 두면 use-case를 더할 때 손대는 것은 옆의 파일 하나로 끝난다. 층의 합성은 자기 층만 보므로 층의 규칙을 깨지 않는다. 층을 넘는 것은 뿌리뿐이고, 예외는 거기서 끝난다.

## 맞는 곳과 맞지 않는 곳

수명이 길고, 외부 서비스가 여럿이며, AI가 대량으로 손대는 코드베이스에 맞는다. 일회용이거나 외부 의존이 하나뿐인 작은 것에는 치르는 수고에 값하지 않는다.
