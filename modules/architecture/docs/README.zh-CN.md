一个以机器可检查的形式,确定依赖方向、文件归属、命名与失败传递方式的 module。规约本身在 [skills/design/SKILL.md](../skills/design/SKILL.md)。

## 读不完的东西,凭什么信任

AI 产出的变更量已经超过了人能读完的量。评审从逐行缩为抽样,很多时候只剩下"还能跑吗"的确认。也就是说,人不再确认 **HOW(怎么写的),而是开始信任 WHAT(做出了什么)**。

这份信任是否成立,不取决于阅读者的耐力,而取决于 **HOW 是否被机制约束住**。没被读到的那部分里潜藏着什么都好:只要形状上写不出来,它就不在那里。

这里有一重矛盾。严格的规约,过去的上限是"人能守住多少"。写不了超过能记住的量,是否被遵守只能靠眼睛确认,于是规约越多越守不住。严格是理想,但代价太高——这是人类时代的行情。

当书写者变成 AI,这个行情就变了。写样板代码的成本几乎消失。而对 AI 而言昂贵的是**猜测该放在哪里**,需要猜测的结构会直接抬高放错位置的概率。严格变便宜了,含糊变贵了。行情反转了。

但约束过头就会扼杀模型的判断力。所以这套规约只约束**结构**,不约束**判断**。层固定为 6 个,层内的 `<kind>` 不固定。边界由规约定下,边界之内解决什么、怎么解决,交给书写者。

## 不是"发现得了",而是"写不出来"

规则的大部分,都从评审需要**发现**的位置,挪到了一开始就**写不出来**的位置。

| 要守住的东西       | 由什么来守                       |
| ------------------ | -------------------------------- |
| 跨层的依赖         | 构建配置(看不见的层无法通过类型解析) |
| 技术词汇渗入内侧   | 根本没有可 import 的外部包       |
| 没有对应端口的适配器 | 文件名规则                     |
| 合成时的注册遗漏   | 类型                             |
| 失败被吞掉         | `Result` 的返回类型              |
| 绕开依赖图         | 不把容器交出去                   |

这不是靠评审找出违规的设计,而是**写下的那一刻就失败**的设计。在没人会读完全部的前提下,这个差别就是安心的量。

位置唯一、名字即说明角色,同样服务于这个目的:它既是人的可读性,也是 AI 更低的检索成本。

## 借了什么,没借什么

| 约定                                     | 出处                       |
| ---------------------------------------- | -------------------------- |
| 依赖永远指向内侧                         | Clean Architecture         |
| 适配器二分为 driving / driven            | 端口与适配器(六边形)     |
| `<bounded_context>` 这一轴、内侧只用业务语言 | DDD                    |
| 合成的根只有一个                         | DI 的 composition root     |
| 失败作为值返回,`throw` 仅限于 bug        | 函数式的错误处理           |
| 按层的构建配置把违规变成编译错误         | 本 module 独有             |
| 测试是层的镜像,镜像同样受依赖规则约束   | 本 module 独有             |

**这不是 Clean Architecture 的实现。** 作为不变式采纳的只有依赖规则,那张图并未照搬。尤其是输出端口(presenter 实现 application 侧端口的形态)没有采用。

**这也不是 DDD 的实现。** 借来的只有 bounded context 与 ubiquitous language 两项,聚合与战略设计的其余部分并未带入。

**层是内外,不是上下。** 与自上而下流动的经典分层不同,依赖永远朝内,外侧不为内侧所知。

## 判断可能分歧之处

规约中本可以有别的选法之处,以及选择的理由。

**`interface` 不看 `domain`。** controller 一旦触碰 entity,领域的形状就会渗进接线的形状。重构领域会开始破坏对外的契约,CA 想要防住的东西又回来了。代价是 use-case 要持有自己的输入输出类型、presenter 要写转换,但那个转换正是边界的翻译。

**`frameworks` 不看 `application`。** 入口有两条时,放在 controller 里的横切处理(认证、校验、错误翻译)会在另一条路径上**悄无声息地漏掉**。不会报错,只是通过了。这是最危险的坏法,所以入口保持一条。

**不使用输出端口。** use-case 驱动 presenter 的经典形态,返回值是 `void`,于是**调用方忽略结果时编译器也保持沉默**。返回 `Result` 的形态,不同时处理成功与失败就通不过类型检查。这里选了类型的强度。

**保留 `ports/` 这一层。** 把端口放在与其他种类相同的高度,"从外部需要的东西的声明"与"自身的逻辑"就无法凭名字区分。付出一级的不对称,换来这个区分是看得见的。

**适配器冠以端口之名。** 相对于 `storage.integration.ts` 的 `google-drive-storage.integration.ts`。满足哪个端口从名字就能读出,没有对应端口的孤儿可以用机器筛掉。

**容器不跨越边界。** 内侧一旦能接过 resolver,不 import 也能取出任何东西。**import 图不再讲述真实的依赖**,构建配置与 linter 都会失效。依赖用参数传。

**合成放在各层级,根只有一个。** 把接线放在代码旁边,增加一个 use-case 时只需动隔壁的一个文件。层的合成只看自己的层,所以不会破坏层的规则。跨层的只有根,例外止于此。

## 适合与不适合

适合长寿命、外部服务有多个、AI 大量参与的代码库。一次性的东西,或外部依赖只有一个的小东西,不值得付出这份手续费。
