# 品質ループ — 憲章の凍結から完了報告まで

全エージェント共通規則(`.agents/` ルートの `AGENTS.md`。以下のパスも同ルート相対)の品質評価の不変条件を前提とし、ここには品質ループの各瞬間の運転規則を置く。

## 凍結

着手前に凍結する: ドメイン言語の合格条件、`共有版レビュー憲章`(目的・合格条件・範囲外・必須の業務ルール。`実装担当` に渡す)、`反証版レビュー憲章`(失敗仮説・独立チェック。レビュアーだけに渡す)。凍結が禁じるのは合格条件と `共有版` の事後の緩和であり、ラウンド中に確定した `欠陥クラス` を `共有版` に蓄積し、以後の `反証版` の反証仮説へ追加することは妨げない。`反証版` には欠落仮説(合格条件のうち実装・検証が存在しないものはどれか)を常に含める。

## 検証とレビューの入力

- `検証`: `完了主張` の証拠は結論ではなく再実行手順で提出させ、レビュー起動前に実装側以外が worktree で独立に再実行する。再実行で確認できない `完了主張` にレビューを起動しない。
- レビューの入力は、元の要望・合格条件・`反証版憲章`・`レビュー対象コミット` から作った専用 worktree・実行方法のみ。走査は合格条件の各項目を起点に、それを満たす実装と検証の存在を実物から探す方向で行わせる。差分・実装側の報告を先に与えない — 注意が「書かれたもの」の検証に占有され、「書かれなかったもの」(欠落)が探索されなくなる。差分は全項目のトレース後の監査でのみ読ませる。
- 報告はスキーマで返させる: `完了主張` は合格条件ごとの実装・検証の対応と再実行手順、レビュー報告は合格条件ごとの判定と指摘リスト(レベル・根拠・再現手順)。作業経過の転写は受け取らず、`マネージャー` の context に入れない。
- ラウンドの記録(指摘リスト、`横展開スイープ`、`再発ガード`、`リスク受容記録`)は会話ではなく bd と成果物に置く。`完了判定` が突き合わせるのはこの外部記録である。
- `サブエージェント` は範囲変更・設計方針の転換・重大リスク・要ユーザー承認を `マネージャー` に戻す(依頼書に明記する)。範囲外の問題は修正させず報告のみ。
- Claude Code では `検証` に `verifier`、`独立レビュー` に `reviewer` のエージェント定義(ハーネス配布物)を使う。ツール制限(両者とも書き込み不可、`reviewer` は実行も不可)が入力と権限の分離を機構で保証する。

## 欠陥クラスと修正ラウンド

指摘を個別に潰さない。指摘は症状であり、`欠陥クラス` はその症状が壊した契約(状態 → 表示 / 操作 → 反応 / 入力 → 業務結果)である。契約を業務の言葉で言語化すると、その契約の持ち主が直す場所になる — 同型が担当範囲に複数あるなら(`横展開スイープ`)持ち主は個別箇所ではなく共有の部品・構造であり、そこを直せば全域に効いてガードは 1 本で足りる。`再発ガード` の層の選択・足し込み型の禁止・検出力の確認は `skills/agents-test-design/SKILL.md` の判断手順に従う。契約を言えないうちは直す場所が決まっていない — 実装ではなく仕様確認・設計に戻り、それでも見つからない単発の症状はガードを作らず `欠陥クラス` を `反証版憲章` に残して閉じる(ガードは永続コスト、憲章は当タスク限りのコストである)。逆にガードにできた `欠陥クラス` は憲章から取り除く。憲章は少数の高信号な失敗仮説に保ち、網羅的チェックリストに育てない。指摘はラウンド単位で収集・トリアージしてから一括修正する(`修正ラウンド`)。

## 指摘レベル(レビュアーの分類が正で、指摘を受けた側は降格できない)

| 指摘レベル     | 内容                                                                           |
| -------------- | ------------------------------------------------------------------------------ |
| `Blocker`      | 要件未達、破壊的回帰、データ損失、重大な安全性問題。                           |
| `Major`        | 完了扱いすべきでない実質的問題(主要シナリオ欠落、仕様解釈ミス、重要な未検証)。 |
| `Minor`        | 完了前に直すべき実問題。                                                       |
| `Inconclusive` | 証拠・環境・要件の不足で判断不能。                                             |

## ラウンドの判定

- `clean`: `Blocker` / `Major` / `Inconclusive` が 0 件。`Minor` は残っていてもよい(下記のとおり修正して閉じる)。
- `reset`: `Blocker` / `Major` / `Inconclusive` が 1 件以上。`修正ラウンド` の後、新規 context の `独立レビュー` を取り直す。
- `Minor` だけの回は `reset` しない。`修正ラウンド` で直し、`修正確認` で閉じる(`独立レビュー` は取り直さない)。`欠陥クラス` の蓄積(`共有版` への追加)は `Minor` でも通常どおり行う。
- 同じ `欠陥クラス` が 2 ラウンド続けて出たら、ラウンドを重ねる前に `マネージャー` が「1 つの仕組みでこの `欠陥クラス` 全体が閉じるか」に答える。閉じない直し方なら手法の失敗であり、直し方から変える。閉じる直し方で閉じ切れていないだけなら実装の失敗であり、そのまま続ける。`Blocker` / `Major` は何ラウンド掛けてでも直す — 減らすのは回数ではなく、1 ラウンドで閉じない直し方のほうである。
- 直し方を変えるときは、失敗した手法が積んだものを残さない。新しい仕組みが覆う範囲の足し込みは、同じ変更の中で撤去して入れ替える。残せば維持コストと誤った安心が永続し、その `欠陥クラス` は閉じない。
- `修正確認`(指摘を出したレビュアー自身による修正の確認)は指摘を閉じる補助であり、`独立レビュー` に数えない。

## 修正ラウンドの担当

- 修正担当は、可能なら元の実装サブエージェントを再利用する(継続メッセージでトリアージ済みの指摘リストを渡す)。
- 渡すのはトリアージ済みの指摘リストと現在の `レビュー対象コミット` のみ。修正担当は着手前に worktree を現在のコミットへ同期する。
- 修正担当が指摘に疑義を持った場合は、修正せず `マネージャー` に報告する。
- 再利用できない・すべきでない場合は、新規エージェントに依頼書(指摘リスト・対象ファイル・再現手順)で引き継ぐ。

## Git 統合

- remote に PR があるブランチは、PR のリモートマージで統合して GitHub 上で MERGED として残す。ローカル squash で取り込むと同じ内容が入っても PR は未マージのまま残り、統合の経緯を GitHub 側から辿れなくなる。統合を依頼されたブランチは、着手前にそのブランチに対する PR の有無を照合する。PR が無いブランチはローカル squash で統合する。
- 古い基点から切ったブランチを潰して統合すると、その間に統合ブランチへ入った**他の作業の成果を巻き添えで消しうる**。潰す前に統合ブランチを取り込んで conflict を解き、その統合が消すファイルの一覧が自分の作業範囲に収まっているかを突き合わせる。範囲外の削除は、レビュー済みの機能が無言で退行した徴候である。
- squash は本 merge 直前に行い、共有 history を壊しうる状況では見送る。
- 統合ブランチは worktree 分割で守れない唯一の合流点であり、単一書き手の原則に従う。並列セッションがありうる環境では、ローカル merge(squash・conflict 解消を含む)は Beads の merge-slot issue(統合の排他ロック)を保持している間だけ行う。
- worktree の存在は「ここで作業が進行中」という宣言である。役目を終えた worktree に、そこにしか無い成果を残さない(レビューの成果は指摘リストに、実装の成果はコミットとブランチに残す)。撤去できない未 commit の変更は、放置せず内容を確認して回収か破棄を判断する。
- merge と `完了判定` の締めに、そのタスクのために切った worktree を撤去する。

## 完了ゲート(すべて必須)

- `独立レビュー` の `clean` が最終の `レビュー対象コミット` に対して 1 回。1 回 = 新規 context の `敵対的レビュアー` × `レビュー対象コミット`(単独作業は `完了主張` のコミット、並列作業は `マネージャー` が統合したコミット)の専用 worktree。
- `修正ラウンド` ごとに、指摘ごとの「壊れた契約 → 直した場所」の対応、`横展開スイープ`、`再発ガード` の判断が記録されており、検証済み。ゲートが要求するのは判断であってガードの本数ではない。前回指摘の未修正・再発なし。
- worktree で lint と担当範囲の spec / test が通過し、各 issue の合格条件と実装状態、bd 上の遷移(close、統合待ちは merge-ready。自 actor の in_progress 残置なし)を突き合わせ済み。develop と conflict なし。設計方針の転換はユーザー合意済み。
- 完遂した issue の子に open が残っていない(`bd children` で確認)。残すものは defer への遷移か、切り出しのユーザー合意がある。
- `完了判定` では、済んだ issue を閉じ、今回の変更が無効化・重複化・充足した近傍の issue を関係グラフに沿って close し(全一覧の巡回はしない)、他の open issue の前提を無効化していないか、`停滞・循環` がないかを確認する。
- `Inconclusive` は原則 `clean` を止める。受容できるのは合格条件の外で影響が限定的な場合のみで、該当 issue に `リスク受容記録`(理由と再確認条件)を残す。記録済みの `Inconclusive` は `clean` の集計から除外する(他が 0 件ならその回は `clean`)。ユーザーに見えうるリスクの受容はユーザーに引き上げる。

## 完了報告

最終報告は、ユーザーが続きの判断に必要な情報が揃っていることを基準とする。次を簡潔に答え、該当が無い項目は「なし」と明示する。

- **完遂した issue**: id と合格条件と bd 上の最終ステータス
- **品質ゲート**: ラウンドごとの `Blocker` / `Major` / `Minor` / `Inconclusive` の件数と判定(`clean` / `reset`)。確かめていないことは確かめていないと述べる
- **成果物**: 業務上の対象について、着手前と完遂後の状態、および変化を確認する方法
- **スコープ外の残課題**: 新たに起票した issue の id・内容・ステータス
- **ユーザーの判断待ち事項**
- **セッション終了判定**: worktree と branch の状態、このセッションを安全に終了できるか
