# テスト設計 — 契約を特定し、正しい場所を直す

対象はユニット・統合・ブラウザー・E2E のすべてのレイヤー。テストの配置・実行コマンド・カバレッジ設定は対象外とし、各プロジェクトのテスト正本に従う。

## 契約

テストが固定してよいのは**契約**だけである。契約とは次の 3 形をいう。

1. **状態 → 表示**: この状態のとき、この情報がこう見える (未承認の目標は操作不可として表示される)
2. **操作 → 反応**: この操作をしたとき、こう反応する (全件削除しても提出は受理され、月自体は残る)
3. **入力 → 業務結果**: この入力のとき、この業務結果になる (権限のない対象への操作は拒否される)

## 手順

### 1. 症状から契約を言語化する

指摘は症状である。「入力欄が見切れる」は症状であって契約ではない。壊れていた契約は「操作に必要な要素は、利用者が到達できるどの表示条件でも操作可能である」かもしれないし、単に「この部品は親の幅に収まる」かもしれない。どちらであるかを確定させる。

**契約が言えない間は、直す場所が決まっていない。** ここで実装に手を付けると、症状が消えた場所だけが直り、添えるテストは再現条件の写しになる。仕様確認・設計に戻る。

### 2. 契約の持ち主を特定する = 直す場所

契約には持ち主がいる。持ち主が修正箇所である。

- 契約が個別の画面・機能のものなら、そこを直す。
- 同じ症状が他所でも起きうるなら、持ち主は個別箇所ではなく**共有の部品・構造**である。部品側で発生条件を持てなくする (寸法契約の強制、収縮下限の既定化、通らない経路を型で作れなくする)。1 箇所の修正が全域に効き、テストは部品の契約に対して 1 本で足りる。

同型が複数見つかったのに個別に直しているなら、持ち主を取り違えている。手順 1 に戻る。

### 3. 契約を、機械的に守れる最も下位の層で固定する

- **(a) 発生条件を持てない設計** — 型・API の形・部品の既定値で、そもそも壊せなくする。テストは要らない。
- **(b) 型・lint** — 設計で消しきれないが、機械的に判定できるもの。
- **(c) 契約テスト 1 本** — 業務ルール・分岐・境界値はユニット / 統合で固定する。ブラウザー実行は実 DOM・フォーカス・キーボードなど**ブラウザーでしか確かめられない契約**に限る。E2E は主要導線の薄い確認に限る。

上位で封じられたら下位は作らない。上位を後から入れたら、それが覆う下位は撤去する。契約が消えたら(機能の廃止・仕様の撤回)、それを固定していたガードも同じ変更の中で撤去する。ガードは資産であると同時に、実行資源と保守を食う永続コストである。

**足し込み型は採らない。** 守備範囲が人の列挙で決まるものは、1 本でもガードに数えない。典型:

- 対象を人が列挙する登録簿・allowlist・除外宣言(実装が増えるたびに 1 件ずつ足す)
- 現状の件数を上限として凍結する台帳(減らしたら再生成が要る)
- 症状の字面を集めた禁止語リスト

いずれも足し忘れると検査が静かに空白になり、実装が増えるたびに追随の手間が永続する。既存のガードがこの形なら、**それを直すことがその `欠陥クラス` の直し方である** — 個別の抜けを足すことではない。列挙が必要に見えたときは、列挙を減らすのではなく列挙が不要な構造へ寄せる。寄せられないならガードを作らない(停止条件を参照)。

守りたい状態は望ましい宣言の存在で固定し、禁止形の不在で検査しない — 禁止形の検査は、その行を消すだけで通る。

### 4. 検出力を一度だけ確認する

修正した実装を戻すと、そのガードが落ちること。落ちないガードは何も固定していない。この確認は作成時に 1 回だけ行う。変異で検出力を測るときは、変異が実物に当たったことを確認してから走らせ、無変異の対照も測る — 道具の壊れ方は、対象に問題があるという結論と見分けがつかない。実装者が想定した変異形だけでなく、現実的な退行の形 (行削除、注記の付加、記法の変更) でも回避できないかを見る。

常設にしたくなったら、それは「このガードが黙って効かなくなっているかもしれない」という不安である。正しい応答は見張りを足すことではなく、ガードの層を下げることである — 発生条件を持てない設計や型で封じたガードは、壊せばその場で落ちるので見張る対象が存在しない。下げられないならガードを作らない。

判定は段数ではなく持ち主で行う。**その検査が守っている契約が業務側 (状態 → 表示 / 操作 → 反応 / 入力 → 業務結果) に無いなら、足場を守る検査であり作らない。** ただし製品そのものが検査器 (linter・テストフレームワーク) なら、そのルールは業務の契約であり、この限りではない。

## 参照してよい値

業務の言葉で説明できるものに限る (「承認済み」「提出済み」「権限がない」「空である」)。説明に座標・ピクセル・内部文字列・実装の閾値が必要になった時点で、契約が特定できていない徴候である。手順 1 に戻る。

- 境界値は**業務の境界** (0 件、上限、期限当日、権限の境目) に限る。実装の境界 (バッファーサイズ、内部閾値) は実装と一緒に動くため固定しない。
- テスト名は「条件 + 期待結果」で書く。症状名 (「見切れない」「重ならない」) がテスト名になるのは、契約が言えていない徴候である。
- モックの戻り値をそのままの検証、呼び出し回数だけの検証、内部関数の呼び出し順・中間状態の固定は、対象の振る舞いではなくテストの配線を検証している。
- 入れ替え作業で「旧い入口と新しい入口が同じ結論を出す」ことを固定しない。旧い入口が新しい入口への薄い委譲なら、同じ経路を 2 度通る恒真テストであり、検出力が無いまま同値が守られていると誤読させる。契約は新しい入口を直接叩いて固定する。
- カバレッジ数値・テスト件数を上げることを目的にテストを追加しない。件数は守りの量ではない。

## 対照例

### 幅 375px で送信ボタンが画面外に出る

- ✗ 幅 375 でボタンが viewport に収まることを assert するブラウザーテスト。守るのはその 1 画面・その 1 幅だけで、正当なデザイン変更でも落ち、幅の前提が変わると**黙って通り続ける**。
- ✓ 契約は「操作に必要な要素は、到達できるどの表示条件でも操作可能である」。持ち主は共有のレイアウト部品なので、部品側で収縮下限と折り返しを既定にする (3-a)。テストは部品に対して「収まらない幅では折り返す」1 本。個別画面のテストは 0 本。

### 他人の目標を編集できてしまう

- ✗ 「目標編集で他人の id を渡すと拒否される」を E2E で 1 本。守備範囲が点で、かつ下位で固定できる契約をブラウザーに置いている。
- ✓ 契約は「権限のない対象への操作は拒否される」(入力 → 業務結果)。持ち主は認可層。同型が他の操作にもあるなら、認可を通らない経路を型で作れなくする (3-a) うえで、認可のユニットテスト 1 本。

### 集計が 1 件ずれる

- ✗ `expect(total).toBe(42)`。今日の fixture でたまたま 42 になる値であり、その変更が退行か正当な変更かをテストは判定できない。
- ✓ 契約は「締め日をまたぐ申請は翌月に計上される」。値そのものに業務上の意味があるなら、仕様値と実装値の一致を確認する形にする。

### lint ルールを追加したあと

- ✗ そのルールが発火することを確かめるテストを常設する。守っているのは lint の設定であって業務の契約ではなく、ルールを書き換えるたびに追随が要る。
- ✓ 導入時に違反コードを 1 度書いて、ルールが落ちることを確認する。以後は確認しない。ルールが黙って無効化される経路があるなら、監視を足すのではなく、その経路 (除外指定の乱用、設定の分散) を塞ぐ。

## 壊れた検査に遭遇したら — 直す前に存在資格を審査する

壊れた・不安定な・遅い検査の既定動作は「直す」ではない。見張りの修理は新たな見張りを生み、修理の集積は足場の手入れを仕事の主流にする。直す前に 3 問で存在資格を審査する:

1. **この検査が守っている契約は業務側にあるか。** 無ければ足場の検査であり、修理ではなく撤去の候補である(手順 4 の判定と同じ)。
2. **層を下げれば、見張り自体が不要にならないか。** 発生条件を持てない設計・型で封じられるなら、修理せず沈めて撤去する(見張りは足さず、沈める)。
3. **削除したら、何が守られなくなるか。** 業務の言葉で答えられなければ削除する。「以前それで事故があった」が答えなら、その事故が壊した契約を 1 で言語化し直す。

同型のまま直してよいのは、この審査を通った(業務契約があり、これ以上層を下げられない)検査だけ。審査の結論は修理 issue ではなく、観測した作業 issue のラウンド記録に残す。

## 停止条件

- 壊れていた契約を業務の言葉で言語化できない → テスト実装ではなく契約の特定 (仕様確認・設計) に戻る。
- テストを通すために fixture・閾値・前提条件の調整を 2 回以上繰り返した → そのテストは契約を参照していない。手順 1 に戻る。
- 契約も一般化も見つからない単発の症状 → **テストを書かず**、スナップショット差分・検品・利用者の報告で拾う。書かない判断と理由を記録して止まる。無理に固定した 1 本は永続コストとして残り、実行資源を契約テストから奪う。

## レビュー時の徴候

次を見つけたら、契約が特定されないまま症状が固定された疑いがある。

- テスト名が症状の否定形である
- fixture に「この値でないと再現しない」値があり、その由来が業務で説明されていない
- assertion がピクセル値・座標・要素寸法の大小比較である
- テストの前提が成立していることを確認する補助 assertion がある (足場を守る検査の兆候)
- 同じ部品に対して、症状違いの spec が複数並んでいる (契約の持ち主が固定されていない)
- そのテストが何の契約を守っているか、誰も言えない

これらは**目視の徴候**である。常設の機械検査にしない (手順 4)。
