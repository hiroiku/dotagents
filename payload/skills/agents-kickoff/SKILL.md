# 着手前 — 不確実性を潰してから凍結する

全エージェント共通規則(`.agents/` ルートの `AGENTS.md`。以下のパスも同ルート相対)を前提とし、ここには着手前と組成の運転規則を置く。凍結する対象(合格条件・憲章)と以後の運転は `skills/agents-quality-loop/SKILL.md` にある。

## 着手前

凍結は強力だが、間違ったものを凍結すると以降の全ラウンドがその上に積み上がる。品質の律速は実装力ではなく、着手前に不確実性をどれだけ潰せたかである。合格条件を凍結する前に、何を凍結すべきかが定まっているかを確かめる。

- `盲点洗い出し`: 対象領域について自分が知らないことを先に列挙する。ユーザーも `マネージャー` も土地勘の無い領域ほど先に行う。
- 設計を左右する曖昧さはユーザーに問う。判断の連鎖をほどく必要があれば `/grilling` / `/grill-with-docs` を使う。
- 似た問題を解いている既存コード・テスト・ルーブリックを先に渡す。文章の仕様より情報量が多い。
- 対象領域の構造(シンボルの所在・呼び出し経路・影響範囲)は、index のあるプロジェクトでは codegraph で導出してから凍結に進む。grep と Read の往復で近似しない。
- 対象領域の open issue(`bd list -l context/X`、deferred 含む)を読み、回収するもの・しないものを合格条件に明示する。
- 主観的な合格条件(見え方・使い心地)は、実装前に複数案を試作して確定させる。
- ここで潰しきれなかったものは `既知の未知` として憲章に残す。実装中に確定したらその場で記録し、完了報告まで持ち越さない。

## issue への着手

issue への着手前に、その合格条件と前提が現状でも成り立つかを確認してから始め、同期状態を保つ。

## サブエージェントの組成

- 既定はセッションと同じモデル・同じ reasoning effort。機械的で指示が具体的な作業(単純実装・置換・列挙・トリアージ済み指摘の反映)だけ下位へ、統合・セキュリティ・難しい設計判断は上位が使えるなら上位へ。迷えば既定のまま。
- 上位または同じ指摘レベルが繰り返され改善されない場合、まず直し方を疑う(agents-quality-loop の `ラウンドの判定` の停止条件)。直し方が正しいうえで難度が理由なら、起動するサブエージェントのモデルを一つ上位に上げて良い。

## 並列化の条件

- 並列化は worktree を分けられる単位に限る。1 つの worktree の書き込み担当は同時に 1 人。全単位が触る共有部分は先行タスクに切り出す。大規模な並列化(Dynamic Workflow 等)は、大きく機械的な work-list があるときだけ使う。
- 次の条件を満たす場合はユーザーにレーン数を確認してから並列起動して良い:
  - 探索範囲が分離され、重複探索によるコンテキストコストが小さい
  - 更新対象が分離され、ファイルやデータの競合がない
  - 責任範囲と判断領域が分離されている
  - タスク間の依存が弱く、安全かつ明確に分割・統合できる

## 依頼書

- `BEADS_ACTOR` / `BEADS_ISSUE_ID`(Beads の actor 名と issue ID)の値を明記する。branch / worktree はこの値から命名する:
  - branch: `{BEADS_ACTOR}/{BEADS_ISSUE_ID}`、派生 branch: `{BEADS_ACTOR}/{BEADS_ISSUE_ID}-*`
  - worktree: `{BEADS_ISSUE_ID}`、派生 worktree: `{BEADS_ISSUE_ID}-*`
- `サブエージェント` のシェルには `BD_READONLY=1` を与える(bd への書き込みは機構で禁止される。読み取りは通常どおり)。
- 範囲変更・設計方針の転換・重大リスク・要ユーザー承認は `マネージャー` に戻すことを明記する。範囲外の問題は修正させず報告のみ。
- 報告スキーマ(合格条件ごとの実装・検証の対応と再実行手順)を指定する。形式は agents-quality-loop の `検証とレビューの入力` にある。
