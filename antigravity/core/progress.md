この節と、「Git」の「ブランチとマージ」、「GitHub」は、利用者とやりとりするメインのセッションが、依頼の受け付けからマージとリリースまでの進行で従うルールである。作業は issue ではなく、依頼された成果物の単位で管理する。実装を自分で行うか、サブエージェントに任せるかは、利用者の設定に従う。

### 依頼の受け付け

- 依頼を、使う人から見た変化として言い直し、実装する内容と設計を実装前にまとめて決める。解釈によって実装する内容が変わるときや、完了の時期や範囲を大きく変えるときは、着手前に利用者に伝え、返事を待たずに進める。

### 作業の分割

- issue ごとに作業を分けると、準備、コンテキストの把握、マージの固定費を毎回払う。同じ場所を触る、同じ知識が要る、同じリリースに入る issue を 1 つのバッチ(作業のまとまり)にまとめ、1 つのブランチで実装して 1 回でマージする。sub-issue には分けない。
- 見込みの時間は、作業の大きさの目安として伝え、膨らんだときに止める判断に使う。約束した予定ではないので、見込みを積み上げて着手の日時や順番の予定を立てず、前の作業が終わったら次の作業に着手する。着手を後に回すのは、ほかの作業の結果、利用者が指定した時期、外部の状態(CI、レビューの返事など)を待つときだけにする。

### チェックの実行

- edit のチェック(変更したファイルの lint と型)はファイルを編集するたびに、commit のチェック(変更したファイルと、それに依存するテスト)はコミットの前に実行する。push 時のチェック(マージ後の全体の型とビルド、主要な経路)はバッチを push する前に 1 回、リリース前のチェック(全体のテスト、E2E)はリリースの前に実行する。
- チェックは、下の「このプロジェクトの設定」の「チェックのコマンド」(`.agents/dotagents.jsonc` の `checks`)にあるコマンドで実行する。節が無ければ、プロジェクトにある既存のコマンド(タスクランナーの定義、CI の workflow)から選び、`.agents/dotagents.jsonc` の `checks` に書くことを利用者に提案する。
- 重いチェックと CI の完了を、待つだけのコマンドで待たない。失敗したら、そのチェックだけに絞って修正する。
- CI はローカルよりリソースが少なく、実行のたびに費用がかかり、月の上限に達すると止まることがある。CI で何が実行されるかを CI の workflow で調べ、ローカルで通してから push する。失敗したらローカルで再現して修正し、修正できたかを見るために push し直さない。続けて終わるバッチをまとめて push すると、CI の実行回数は減るが、マージは遅れる。

### レビュー

- 認可、金銭、データの整合性、取り消せない移行、公開している API や保存形式、広く使われる部品に触れる変更は、実装した本人とは別の観点で検証する。別の観点の検証は時間と費用がかかるので、ほかの変更には行わない。検証はバッチごとに 1 回、差分の全体に対して行う。検証の手段は、利用者の環境に任せる。
- 修正するのは、再現が示された要件の未達と、この変更が壊したものである。修正では、再現を失敗するテストとして先に書いてから直す。同じ種類の指摘が別のバッチでも出たら、型、lint、テスト、共通の部品で 1 か所で検出できるようにする。
- 見込みを大きく超えた、同じ指摘が残った、修正が新しい不具合を持ち込んだ、のどれかが起きたら、場当たり的な修正を重ねずに要件を読み直し、設計を見直す。
