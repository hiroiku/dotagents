# リリース手順

リリースすることと、リリースしないと決めることは、外部に影響する操作である。プロジェクトが委任していなければ、利用者に確認してから行う。

- バージョンを上げる場所(ファイルのバージョンか、tag だけか)と、tag を付ける時期とブランチは、プロジェクトのリリースの決まりと、採っている git の運用に従う。決まりが無ければ、ファイルのバージョンを上げてコミットし、そのコミットに tag を付ける。
- 1 つのリポジトリーから複数の製品を別々にリリースするときは、バージョン、tag、GitHub の Release、マイルストーンを製品ごとに扱う。
- リリースの前に、リリース前のチェック(全体のテスト、E2E)を実行する。`ARCHITECTURE.md` があれば、`architecture` のスキルに沿って見直す。
- リリースの中身は、tag を付けた時点でデフォルトブランチにマージされているもので決まる。マイルストーンを使い、プロジェクトに決まりが無ければ、tag を付けるときに、マージ済みの issue は、次のバージョン向けのマイルストーンにあったものも、このリリースのマイルストーンへ移す。このリリースのマイルストーンにあって終わっていない issue は、次のバージョンのマイルストーンへ送る。
- 前回のリリースは、同じ製品で最後に公開したリリース、つまり GitHub の Release があるバージョンを指す。tag だけ付けてリリースしなかったバージョンは数えない。リリースしなかったバージョンを起点にすると、使う人がまだ受け取っていない変更が本文から漏れる。
- リリースするたびに、そのバージョンの tag で GitHub の Release を作る。名前は、プロジェクトに決まりが無ければ tag と同じにする。本文には、前回のリリースから何が変わったかを、使う人にとっての変化として書く。コミット、ファイル、内部の識別子の名前は並べない。末尾に、前回のリリースの tag との比較へのリンクを付ける。
- 何が入ったかは、前回のリリースの tag 以降のコミットで決める。マイルストーンは予定なので、本文の元にしない。
- マイルストーンを使い、プロジェクトに決まりが無ければ、リリースしないと決まったバージョンのマイルストーンは、中身を次のバージョンのマイルストーンへ移してから閉じる。tag は消さない。
- tag や GitHub の Release を workflow が作るリポジトリーでは、自分では作らずに、できた Release の本文を更新する。
