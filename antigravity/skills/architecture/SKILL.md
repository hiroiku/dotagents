# ARCHITECTURE.md

`ARCHITECTURE.md` は、初めてこのリポジトリーで作る人とエージェントが、どこに何があり、何を壊してはいけないかを知るための地図である。根に 1 つ置く。プロジェクトの AGENTS.md と README からは、このファイルを指すだけにし、中身を写さない。

## 書くこと

めったに変わらず、ファイルを 1 つ開いても分からないことだけを書く。

- 見取り図: 何をする製品で、どんな部品(配備の単位、コンテキスト、パッケージ)に分かれ、要求とデータがどう流れるか。
- 地図: 部品ごとの置き場と責務。「X をしているのはどこか」に答えられる粒度にし、ファイルを並べない。部品の内側は、そのそばの文書かコメントに任せる。
- 不変条件: 破ると作りが壊れる決まり(何が何を import しないか、どこだけが書き込むか、何を同期で待たないか)。コードを読んでも見えない「無いこと」ほど書く。
- インフラ: 何がどこで動くか、使っている外のサービスとアカウント、コードの外で設定したもの(管理画面の設定、DNS、秘密の置き場の名前)。IaC に書いてあるものは書かず、その置き場を指す。秘密の値は書かない。
- 横断する決めごと: 認可、エラー、ログ、設定、テストの置き場のように、部品をまたいで同じにしていること。

図は、文字で書ける形(Mermaid など)で同じファイルに置く。画像は差分で読めず、エージェントが直せない。

## 書かないこと

- ファイルを見れば分かること(依存と版、コマンド、設定の値、IaC の中身)。写すと、片方だけが直されて食い違う。
- 常設の文(設計の形、layered)にある決まり。書くのは、このプロジェクトでの当てはめ(コンテキストの名前と置き場、決まりからの例外)だけにする。
- なぜそう選んだか。比べた案と理由は issue か設計の文書に残し、ここには結論とリンクだけを書く。
- 予定、進み、作りかけのもの。古くなる時期が読めない。

## 古くしない

- 作りを変える変更(部品を足す、消す、分ける、境界や依存の向きを変える、外のサービスやインフラを足す、替える)では、同じコミットで `ARCHITECTURE.md` を直す。別のコミットにすると、片方だけが取り込まれる。
- 書いた不変条件と、地図に書いた置き場は、プロジェクトの lint かチェックで落とす(依存の向き、置き場が実在すること)。ハーネスはチェックの道具を配らない。無ければ作ることを利用者に提案し、作ったらチェックの段階に置く。
- 版を切る前に、前の版から後の変更と見比べて見直す。合わない記述は直し、指すものが無くなった記述は消す。
- 全体を毎回読める長さに保つ。長くなったら、詳しい部分を部品のそばの文書へ移し、ここには地図を残す。

## 初めて書くとき

コードと設定から推した案を作り、利用者に見せてから書く。依存の向きは import から、配備の単位は IaC と workflow から、外のサービスは設定と環境変数の名前から推す。推せないこと(コードの外で設定したもの、外のアカウント、守ってきた不変条件)は利用者に尋ね、推したことと分けて示す。
