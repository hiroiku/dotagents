# ARCHITECTURE.md

`ARCHITECTURE.md` は、このリポジトリーで初めて実装する人とエージェント向けに、採っている技術、部品の配置、壊してはいけない不変条件を、それぞれの理由と見直す条件と一緒に示す文書である。ルートに 1 つ置く。プロジェクトの AGENTS.md と README からは、このファイルへのリンクだけを置き、中身をコピーしない。

## 記載する内容

めったに変わらず、ファイルを 1 つ開いても分からないことだけを書く。決めたことには、理由と見直す条件(日付ではなく条件)を添える。理由があれば、書いていない場面でも同じ方針で判断でき、条件があれば、いつ改めるかが分かる。

- 技術の選定: 採っている言語、フレームワーク、データベース、主な外部サービスと、それを選んだ理由。
- 全体像: 何をする製品で、どんな部品(デプロイ単位、bounded context、パッケージ)に分かれ、リクエストとデータがどう流れるか。
- 部品の配置: 部品ごとの配置場所と責務。「X をしているのはどこか」に答えられる粒度にし、ファイルを並べない。部品の内側は、そのそばの文書かコメントに書く。
- 不変条件: 破ると構成が壊れる決まり(何が何を import しないか、どこだけが書き込むか、何を同期で待たないか)。「〜しない」という決まりはコードを読んでも分からないので、特に書く。
- インフラ: 何がどこで動くか、使っている外部サービスとアカウント、コードの外で設定したもの(管理画面の設定、DNS、シークレットの保管場所の名前)。IaC に書いてあるものは書かず、その場所を指す。シークレットの値は書かない。
- 横断する決めごと: 認可、エラー、ログ、設定、テストの配置のように、部品をまたいで同じにしていること。

図は、テキストで書ける形式(Mermaid など)で同じファイルに置く。画像は差分で読めず、エージェントが更新できない。

## 記載しない内容

- ファイルを見れば分かること(依存の一覧とバージョン、コマンド、設定の値、IaC の中身)。コピーすると、片方だけが更新されて食い違う。
- エージェントの作業の手順(環境の準備、ファイルからは読み取れない道具の使い方、作業の進め方)。AGENTS.md に置く。
- 常時読み込まれる指示(レイヤー構成、layered)にある決まり。書くのは、このプロジェクトでの当てはめ(bounded context の名前と配置場所、決まりからの例外)だけにする。
- 選ぶまでの経緯。比べた案と議論は issue か設計の文書に残し、ここには結論、理由、見直す条件と、経緯へのリンクを書く。
- 予定、進み具合、作りかけのもの。いつ古くなるかが読めない。

## 更新の運用

- 技術の選定や構成を変える変更(技術を採る、替える、部品を追加する、削除する、分ける、境界や依存の向きを変える、外部サービスやインフラを追加する、置き換える)では、同じコミットで `ARCHITECTURE.md` を更新する。別のコミットにすると、片方だけがマージされることがある。
- 書いた不変条件と、「部品の配置」に書いた配置場所は、プロジェクトの lint かチェックで違反を検出する(依存の向き、配置場所が実在すること)。ハーネスはチェックツールを配布しない。無ければ作ることを利用者に提案し、作ったら `.agents/dotagents.jsonc` の `checks` に書く。
- リリースの前に、前回のリリース以降の変更と見比べて見直す。合わない記述は更新し、指すものが無くなった記述は消す。
- 全体を毎回読める長さに保つ。長くなったら、詳しい部分を部品のそばの文書へ移し、ここには部品の配置を残す。

## 新規作成

コードと設定から推測した案を作り、利用者に見せてから書く。依存の向きは import から、デプロイ単位は IaC と workflow から、外部サービスは設定と環境変数の名前から推測する。推測できないこと(コードの外で設定したもの、外部のアカウント、守ってきた不変条件)は利用者に確認し、推測したことと分けて示す。
