# 共通ルール

目的は、頼まれた成果を、設計として最も良い形で届けることである。進め方は状況を見て自分で決める。ここにある進め方は既定である。利用者の指示やプロジェクトの決めごとと食い違うときは、そちらに従い、食い違いを知らせる。

- 取り消せることは、確かめずに決めて進める。止まって確かめるのは、取り消せない操作と、手元の外(本番、公開、人、お金)へ届く操作だけにする。プロジェクトが任せると決めた種類は、確かめない。
- 報告には、利用者から見えて変わること、自分で決めた前提、改めた決定、見つけた別の問題を、漏らさず書く。記号や内部の呼び名に頼らず、それだけ読んで分かるように書く。
- プロジェクトの作り(部品の境界、依存の向き、外のサービスとインフラ)は、根の `ARCHITECTURE.md` にある。あれば作る前に読み、作りを変えたら同じコミットで直す。書き方は architecture のスキルにある。

## 設計を選ぶ

作りは、今の作りに近いかや、よく使われているかではなく、次の性質で選ぶ。

- 安全: 権限の無い操作にも、あってはならない状態にも、どんな入力からも到達できない。権限のチェックは入口の 1 か所で通し、あってはならない状態は型で表せなくする。
- 安定: 順番、同時の実行、途中の失敗、同じ操作の 2 回目で結果が変わらない。壊れたときは壊れたと分かり、人の手なしで元に戻れる。
- メンテナンス性: 1 つの事実は 1 か所にだけ持ち、一覧も含めて、ほかはそこから導く。変わりにくい中心が、変わりやすい詳細に依存しない。
- パフォーマンス: 必要な仕事の量を超える計算、記憶、待ちを、構造として作らない。件数に比例する往復や、並べられる待ちの直列を作らない。
- スケーラビリティ: コード、データ、利用者のどれが増えても、上の 4 つが保たれる。

1. 案を考える前に、問題が求める性質を書く。あってはならない状態、同時に起きうること、正の置き場、何が何倍に増えるかである。
2. 案には、今の作りの延長のほかに、問題を構造として起きなくする案を入れる。知らない領域では、設計の質で評価されている製品の解き方、使える部品、ほかの作りの壊れ方を外で調べる。
3. 5 つを同時に満たす作りを探す。そういう作りは、状態と部品が少ない。両立しないときだけ上にあるものを優先する。最初の手間は比べる軸に入れず、選んだあとで知らせる。
4. 症状を隠す案(キャッシュ、チェックの追加、例外の分岐)は、原因をなくす案が成り立たないと示せたときだけ選ぶ。
5. 選んだ理由、譲ったもの、見直す条件を、issue か設計の文書に残す。この基準は長く残るものに掛け、捨てる試作には掛けない。

## 確かめる

- 決まりと不変条件は、文やレビューではなく、型、lint、テストで落ちるようにする。軽いチェックで落ちるものを、重いチェックに任せない。
- テストは、回すたびに時間と CI の費用を使い、作りを変えるたびに直す手間になる。確かめるのは使う人や業務から見た振る舞いにし、構造だけを変えても落ちないようにする。
- 文言、色、配置は試さない。フォーカスの行き先や読み上げは振る舞いなので、ブラウザーを起動しないテストで確かめる。ブラウザーと E2E は、業務の責務として説明できる経路に絞る。
- 型、lint、ほかのテストが落とすことに、テストを足さない。ソースを文字として読むチェック(未使用、構造、命名、配置)は lint として、振る舞いのテストと分ける。

## 前の決定

前の決定と、issue に書かれた直し方は、文面ではなく、守ろうとした意図を読む。作りが変わって合わなくなっていれば、意図に沿って改め、報告に書く。意図そのものを変えるときは、利用者に知らせてから進める。

# 設計の形(layered)

層は `app-kernel`、`domain`、`application`、`interface`、`infrastructure`、`frameworks` の 6 つで、依存は外から内へ向ける。import してよいのは次の層だけである。

- `app-kernel` は、ほかの層を import しない。
- `domain` は `app-kernel` だけ。外のパッケージと、ほかのコンテキストも import しない。
- `application` は `domain` と `app-kernel`。外のパッケージは import しない。
- `interface` と `infrastructure` は `application` と `app-kernel`。
- `frameworks` は `interface` と `app-kernel`。例外は、下に書くコンポジションルートだけである。

この向きは、文やレビューではなく、プロジェクトの lint かチェックで落とす。チェックを通すために例外を足さない。

- 置き場は `src/<層>/<種類>/<コンテキスト>/<名前>.<種類>.ts` を既定にする。
- `domain` は業務の概念と規則を持ち、bounded context ごとに分ける。コンテキストをまたぐ調整は `application` が持つ。
- `application` はユースケースを持つ。外に求めるものは `application/ports/` に業務の言葉で宣言し、実装は `infrastructure` に置く。1 つのアダプターは 1 つのポートを実装し、名前の前に技術名を付ける。
- `app-kernel` は、この形を動かす部品(`Result`、基底のエラー型)だけを持つ。無関係な製品へ持ち込むときに名前を変える必要があるものは置かない。使う場所が多いことは、ここへ移す理由にならない。
- 技術やベンダーの名前は、`infrastructure` と `frameworks` にだけ現れる。識別子、型名、ファイル名、コメント、エラーの文も同じである。
- 層をまたいで組み立てるのは、配備の単位ごとに 1 つのコンポジションルートだけにする。内側は依存を引数で受け取る。コンテナーやリゾルバーを内側へ渡すと、import のつながりが依存の実態を表さなくなる。
- 型とヘルパーは、所有するもののそばに置く。ユースケースの入出力はユースケース、外とのやりとりの型はポート、行や SDK の型は実装の中が持つ。`dtos/` や `types/` のような置き場を作らない。
- 契約に含まれる失敗は `Result` で返し、`throw` は壊れた不変条件にだけ使う。層ごとのエラーは、境界で外側のエラーへ包み直し、元を `cause` に残す。
- テストは `test/<層>/` に写して置き、写した層と `app-kernel` だけを import する。
