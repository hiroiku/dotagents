# dotagents の既定のルール

ここにある進め方は既定である。利用者の指示、ホストの権限設定(plan モード、許可ルールなど)、プロジェクトの決めごと(AGENTS.md と下の「このプロジェクトの設定」)が、これより優先する。食い違うときは、そちらに従い、食い違いを伝える。

## 基本方針

依頼された内容を、下の「設計」の判断基準に沿って実装する。進め方は状況に応じて自分で決める。

- 取り消せることは、確認せずに決めて進める。利用者に確認するのは、取り消せない操作と、外部に影響する操作(本番、公開、他者への連絡、金銭)だけにする。プロジェクトが委任した種類は、確認しない。
- 報告には、利用者から見えて変わること、自分で決めた前提、改めた決定、見つけた別の問題、実行した確認とその結果、実行しなかった確認、残っている失敗や障害を、漏らさず書く。記号や内部の呼び名に頼らず、それだけ読んで分かるように書く。

## 設計

### 判断基準

構成は、既存の構成に近いかや、広く使われているかではなく、次の性質で選ぶ。

- 安全性: 権限の無い操作と、あってはならない状態を、入力によって起こせないようにする。認可は入口の 1 か所で行い、あってはならない状態は型で表現できないようにする。
- 安定性: 実行順、同時実行、途中の失敗、同じ操作の再実行で結果が変わらないようにする。障害は検知でき、手作業なしで復旧できるようにする。
- メンテナンス性: 1 つの事実は 1 か所にだけ持ち、一覧も含めて、ほかはそこから導出する。変更の少ない中核を、変更の多い詳細に依存させない。一覧や規則を宣言するときは、実態と照合する検査と組にする。
- パフォーマンス: 必要な処理量を超える計算、メモリー、待ち時間を生む構造にしない。件数に比例する往復を作らず、並列にできる待ちを直列にしない。
- スケーラビリティ: コード、データ、利用者のどれが増えても、上の 4 つを保てるようにする。

1. 案を考える前に、あってはならない状態、同時に起こりうること、正とするデータ(source of truth)の持ち場所、何がどれだけ増えるかを書き出す。
2. 案には、既存の構成の延長のほかに、構造上その問題が起きなくなる案を含める。知らない領域では、設計の質で評価されている製品の解き方、使える部品、ほかの構成の失敗例を外部の資料で調べる。
3. 5 つを同時に満たす構成を探す。状態と部品が少ない構成ほど満たしやすい。両立しないときに限り、上に書いた性質を優先する。実装コストは比較の基準に含めず、選んだあとで伝える。
4. 症状を隠す案(キャッシュ、チェックの追加、例外の分岐)は、原因をなくす案が成り立たないと示せたときだけ選ぶ。
5. 選んだ理由、譲ったもの、見直す条件を、issue か設計の文書に残す。この基準は長く使うコードに適用し、捨てる前提の試作には適用しない。

### レイヤー構成(layered)

層は `app-kernel`、`domain`、`application`、`interface`、`infrastructure`、`frameworks` の 6 つで、依存は外側から内側へ向ける。

import してよい層:

- `app-kernel`: なし
- `domain`: `app-kernel`
- `application`: `app-kernel`、`domain`
- `interface`: `app-kernel`、`application`
- `infrastructure`: `app-kernel`、`application`
- `frameworks`: `app-kernel`、`interface`(コンポジションルートは例外)

`domain` は、ほかの bounded context も import しない。

外部パッケージは、性質によって扱いを分ける。

- 純粋な計算のパッケージ(金額の 10 進数計算、日付の計算、検証など)は、`domain` と `application` でも使ってよい。どれを許すかは、プロジェクトが lint の許可リストで決める。ライブラリの型は `domain` の公開する型に出さず、値オブジェクトで包む。
- 実行のたびに結果が変わるもの(UUID の生成、現在時刻、乱数)は、`domain` の中で生成しない。ポートで受け取るか、`application` で生成して渡す。テストで値を固定できるようにするためである。
- I/O、フレームワーク、ベンダーの SDK は、`domain` と `application` で import しない。import するのは `infrastructure` と `frameworks` だけである。

依存の向き、下に書くファイルの配置と命名は、文やレビューではなく、プロジェクトの lint かチェックで検出する。それらを検出する lint がプロジェクトに無ければ、作ることを利用者に提案する。チェックを通すために例外を追加しない。

- ファイルは `src/<層>/<種類>/<context>/<名前>.<種類>.ts` に置くのを既定にする。`<名前>` は、そのファイルが公開する型の名前を kebab-case にしたものである。
- `<context>` は bounded context(同じ言葉が同じ意味を持つ業務の範囲)である。ユースケース、技術の仕組み、外部システムの名前で `<context>` を作らない。ユースケースはファイルで分ける。
- bounded context の名前の一覧と、それぞれが指す業務の範囲(1 文)は、コードの 1 か所で宣言する。範囲の書き漏れは型で検出し、`<context>` の位置のディレクトリー名が一覧にあるかは lint で検出する。照合する lint の無い一覧は、実態とずれても気づけないので作らない。
- `domain` は業務の概念と規則を持ち、bounded context ごとに分ける。bounded context をまたぐ調整は `application` が持つ。
- `application` はユースケースを持つ。外部への依存は、ポート(種類は `port`)として `application` に業務の言葉で宣言し、実装(アダプター、種類は `adapter`)は `infrastructure` に置く。1 つのアダプターは 1 つのポートを実装する。
- アダプターのクラス名とファイル名は、ポートの名前の先頭に、接続先の製品やサービスの名前を付けたものにする。ORM やクライアントライブラリの名前ではなく接続先の名前を使い、外部に接続しない実装には方式の名前を付ける。例: ポート `UserRepository` には `PostgresUserRepository` と `InMemoryUserRepository`、ポート `Mailer` には `SesMailer`。ポート `UserRepository` のファイルは `src/application/port/account/user-repository.port.ts`、アダプター `PostgresUserRepository` のファイルは `src/infrastructure/adapter/account/postgres-user-repository.adapter.ts` に置く。
- `app-kernel` は、この形を動かす部品(`Result`、基底のエラー型)だけを持つ。別のプロダクトに持っていくときに名前を変えなければならないものは置かない。利用箇所が多いというだけでは、ここへ移す理由にならない。
- 技術やベンダーの名前は、`infrastructure` と `frameworks` にだけ現れる。識別子、型名、ファイル名、コメント、エラーの文も同じである。例外は lint で許可した純粋な計算のパッケージで、その名前は `domain` と `application` の import と、値オブジェクトの実装の中にだけ現れてよい。
- 層をまたいで組み立てるのは、デプロイ単位ごとに 1 つのコンポジションルートだけにする。内側は依存を引数で受け取る。コンテナーやリゾルバーを内側へ渡すと、import の関係が実際の依存を表さなくなる。
- 型とヘルパーは、所有するもののそばに置く。ユースケースの入出力はユースケース、外部とのやりとりの型はポート、行や SDK の型は実装の中が持つ。`dtos/` や `types/` のようなディレクトリーを作らない。
- 契約に含まれる失敗は `Result` で返し、`throw` は壊れた不変条件にだけ使う。層ごとのエラーは、境界で外側のエラーに包み直し、元のエラーを `cause` に残す。
- テストは `test/<層>/` に `src/<層>/` と同じ構成で置き、その層と `app-kernel` だけを import する。

### テスト

- 決まりと不変条件は、文やレビューではなく、型、lint、テストで検出する。軽いチェックで検出できるものを、重いチェックに頼らない。
- テストは、実行するたびに時間と CI の費用を使い、構成を変えるたびに更新の手間になる。[Test Desiderata](https://testdesiderata.com/)(Kent Beck)の性質から、対象に必要なものを選ぶ。性質は互いに補うことも、トレードオフになることもある。テストで検証するのは使う人や業務から見た振る舞いにし、構造だけを変えても失敗しないようにする。
- 文言、色、配置はテストしない。フォーカスの移動先や読み上げは振る舞いなので、ブラウザーを起動しないテストで検証する。ブラウザーと E2E は、業務の責務として説明できる経路に絞る。
- 要件が変わって期待値が変わったとき以外は、既存のテストを消す、スキップする、期待値を緩める、のどれかで通さない。テストが誤っているか、要件を満たせないと分かったら、回避せずに報告する。
- 型、lint、ほかのテストが検出することに、テストを追加しない。ソースを文字列として読むチェック(未使用、構造、命名、配置)は lint として、振る舞いのテストと分ける。

### ARCHITECTURE.md

プロジェクトの構成(部品の境界、依存の向き、外部サービスとインフラ)は、ルートの `ARCHITECTURE.md` にある。あれば実装前に読み、構成を変えたら同じコミットで更新する。書き方は `architecture` のスキルにある。

## 決定と記録

過去の決定と、issue に書かれた修正方針は、文面ではなく意図に従う。構成が変わって合わなくなっていれば、意図に沿って改め、報告に書く。意図そのものを変えるときは、利用者に伝えてから進める。

### 記録の置き場所

- issue は作業単位の記録にする。作業が終わっても続く事実は、文書に置く。
- 文書の置き場所は、事実の種類で決める。
  - コードに関する決めごと(仕様、構成、API、開発の手順)は、リポジトリーの docs と `ARCHITECTURE.md` に置き、コードと同じ PR で更新する。
  - エージェントが毎回守る決めごと(採っている技術、ファイルの配置、使うコマンド、レビューで見ないもの)は、AGENTS.md に置く。詳しい仕様や構成は docs と `ARCHITECTURE.md` に置き、AGENTS.md からリンクする。同じ事実を 2 か所に書かない。
  - 業務の決定、運用の手順、利用者向けのマニュアルは、Wiki に置く。Wiki が使えない環境では、`docs/wiki/` に Wiki と同じ形(1 ページを 1 つの Markdown ファイル、トップを `Home.md`)で置き、ほかの docs と同じく PR で更新する。
  - 業務の決定がコードの制約になるときは、理由を Wiki に、制約をコード(型、テスト)に置き、docs からは Wiki へリンクする。同じ事実を 2 か所に書かない。
- issue を閉じるときは、作業のあとも続く決定を上の置き場所へ移し、issue からリンクする。
- 文書には、作業の状態、予定、進み具合を書かない。事実が変わったら書き直し、経緯は issue に残す。

## Git

### コミット

- issue ごとにコミットする。主題には、使う人や業務にとって何が変わったかを書く。プロジェクトにコミットメッセージの規約(Conventional Commits など)があれば、それに従う。issue を終えるコミットの本文に `Closes #番号` を書く。
