# 確かめ方を決める

計測では、レビューの往復のうち、コードの修正につながったのは 2〜3 割だった。作る役の時間の 6 割は、最初のレビューのあとに使われていた。すべての変更に同じ確かめ方を掛けず、壊れたときの影響で決める。

## 頼むかどうか

- 頼む: 認可、お金、データの整合性に触れる変更。取り消せない移行。公開している API や保存する形式の変更。広く使われる部品の変更。
- 頼まない: テストと型で要件が確かめられている変更。文言や見た目だけの変更。内部で閉じた小さな変更。これらは push の段の検査で足りる。
- 頼むときは、束ごとに 1 回、束の差分の全体に対して頼む。issue ごとには頼まない。

## 頼み方

- 渡すのは、満たすべき要件、worktree とコミット、差分の範囲、絞った実行方法である。作る役の報告は渡さない。
- 観点を絞るときは、依頼に書く(セキュリティー、アクセシビリティー)。
- プロジェクトが見ないと決めたものは、宣言の決定として確かめる役にも届いている。依頼に書き直さない。
- 確かめているあいだ、その worktree を変更しない。

## 受け取ったあと

- 直すのは、起きる条件と再現が示された、要件の未達と、この変更が壊したものである。重さの言葉では決めない。
- 直しは、作った役に続けて頼む。指摘の再現を、落ちるテストとして先に書いてから直す。描画しないと分からない指摘は、示された手順で直ったことを確かめる。
- 再確認は、同じ確かめる役に続けて頼み、直しの差分だけを見てもらう。新しい役は前回の指摘を知らずに読み直し、往復が終わらない。
- 直しが新しい不具合を持ち込んだときと、同じ指摘が直しのあとも残ったときは、継ぎ足さずに作り方を見直す。
- 同じ種類の指摘が別の束でも出たら、型、lint、テスト、共通の部品のどれかで、1 か所で落ちるようにする。
- 別の問題として報告されたものは、利用者への報告に載せる。issue にするかは、別に決める。
