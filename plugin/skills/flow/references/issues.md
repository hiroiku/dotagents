# issue

GitHub を前提に書いてある。ほかの道具では、同じ考え方をその道具の仕組みに当てはめる。

## 書く

- 1 つの issue は、取り込んだ時点で動作する範囲にする。
- 作成したら、タイプ、ラベル、マイルストーン、担当者のうち当てはまるものを設定する。値は、その organization とリポジトリーで既に使われているものから選ぶ。
- マイルストーンはリリースの版に使い、名前は版の tag と同じにする。割り当てる版が決まっていないときは付けない。
- 本文は、本文だけを読めばいまの状態が分かる要約に保ち、状態が変わるたびに書き直す。本文に入れるのは、いまの状態(どこまで済み、何が残り、何を待っているか)、決めたこと(決めた日と決めた人)、判断を求めていること(選択肢、おすすめ、トレードオフ)の 3 つである。
- コメントは時系列の記録にする。判明した原因、試して採らなかった方法、途中で見つかった制約を書く。
- 新しいセッションは、会話ではなく issue を読んで続きを始める。続きに要る状態と決定は、issue に置く。

## 着手する前

- issue に書かれた直し方やおすすめが、設計の基準(核の 5 つの性質)に沿っているかを確かめ直す。古い issue は、いまの基準に沿っていないことがある。沿っていなければ、沿う案に改め、改めたことを報告に書く。
- 着手したら、Projects のステータスを進行中に変える。状況が変わったら、その時点の状況に合わせる。

## 閉じる

- issue は、その変更がすべて取り込み先に入ったときに閉じる。閉じた issue は取り込み先に入ったことを表し、本番に出たかはマイルストーンと版の tag で表す。
- issue を終えるコミットの本文に `Closes #番号` を書く。取り込み先がデフォルトブランチなら、push や PR のマージで GitHub が閉じる。デフォルトブランチでなければ自動では閉じないので、取り込んで push したあとに閉じる。
- 一部だけが入った issue は開いたままにし、入ったコミットと残りを本文に書く。
- PR を作ったら、対応する issue にリンクする(`addCloseIssueReferences`)。PR の本文の `Closes` は、base がデフォルトブランチのときしか解釈されない。
- 閉じるときは、実際に起きたことに合う理由を選ぶ。重複は、残すほうを参照して閉じる。

## 見つけた別の問題

- 作業やレビューで見つけた別の問題は、利用者への報告に必ず載せる。
- issue にするかは、報告とは別に決める。利用者が基準を決めていればそれに従い、無ければ、どれを issue にするかを利用者が選べる形で報告する。見つけたものをすべて issue にすると、終える数より増える数が上回る。

## 棚卸し

開いている issue が減らないときに行う。

1. 開いている issue を、古い順に並べる。
2. 1 件ごとに、やる(次の束に入れる)、やらない(理由を付けて閉じる)、戻す(順番を決めずに置く)のどれかを付ける。重複と、すでに直っているものは、やらないに入れる。
3. 1 つの表にして利用者に出し、1 回の確認で反映する。
