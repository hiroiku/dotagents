# 成果を届けるまで

issue 1 件ごとに役と worktree を分けると、用意、引き継ぎ、確かめ直しの固定費を 1 件ごとに払う。計測では、同じ役が続けて作った 2 件目からは 0.4〜0.75 倍の時間で済んだ。ここの手順は、固定費を払う回数を減らすように組んである。

## 受ける

- 頼まれたことを、届ける成果(使う人から見て何が変わるか)として言い直す。読み方が分かれ、どちらを選ぶかで作るものが大きく変わるときは、作る前に、自分の読み方を 1 文で知らせる。返事は待たずに進める。
- 役に渡すと、依頼を書き、役が把握し直し、報告を読む手間が掛かる。その手間より小さい仕事は、自分で片付ける。

## 束ねる

- 同じ場所を触る issue、同じ知識が要る issue、同じ版に入る小さな issue を、1 つの束にする。
- 1 束の量は、作る役が文脈を圧縮せずに終えられるところまでにする。圧縮をまたぐと、決めた設計と前提が抜ける。
- sub-issue には分けない。分けるのは、別々に統合して別々に確かめる必要があるときだけにする。

## 並べる

束を並べると、届くのが早くなる。代わりに、消費が短い時間に集まり、統合の順番待ちと載せ替えが増える。順に進めると、その逆になる。並べる数に決まりは無い。

- 並べられるのは、束どうしが同じ場所を触らず、互いの結果を待たないときである。
- 速さと消費のどちらを取るかの答えが、このプロジェクトで続くものなら、宣言の決定に残す。

## 作る役に渡す

- 依頼には、届けるもの、決めた設計と理由、対象の issue、worktree とブランチ、見込みの時間、範囲の外にあるものを書く。
- 束の途中で分かったことは、同じ役に続けて頼む(Claude Code では SendMessage)。新しい役は、把握し直しから始めることになる。
- worktree とブランチの名前は自由に決める。issue との対応は、コミットで取る。

## 検査の段

| 段 | 何を確かめるか | 誰がいつ |
|---|---|---|
| 編集 | 言語サーバーの診断、変更したファイルの lint と型 | 作る役が、編集のたびに |
| コミット | 変更に依存する単体テスト、lint、増分の型 | 作る役が、コミットの前に |
| push | 取り込んだ組み合わせに対する、型とビルドの全体、主要な経路 | 進める役が、束ごとに 1 回 |
| 版 | 通しのテスト、E2E、カバレッジ | 進める役が、版を切る前に |

- プロジェクトの宣言に段ごとのコマンドがあれば、それを使う。無ければ script と workflow を読んで決め、宣言に書くことを提案する。CI も同じ入口を呼ぶ形にする。
- push の段が失敗したら、失敗した検査だけに絞って直す。全体は回し直さない。
- 版の段を、版を切る前より早く回すかは、落ちたときに戻る範囲と、回す消費を比べて決める。プロジェクトが時期を決めていれば、それに従う。
- 時間のかかるコマンドと CI は裏で動かし、完了の通知を受け取る。sleep や出力ののぞき直しで待たない。

## 統合する

- 取り込む前に、作業ブランチを最新の統合先へ rebase する。追従に merge は使わない。
- issue ごとのコミットを残して取り込む。統合先が保護されていれば PR で取り込む。squash するときは、終えた issue すべての `Closes #番号` を本文に書く。
- PR は draft で開き、検証が済んだら ready にする。push や PR で何が走るかは、workflow で確かめる。
- 取り込んで push したら、worktree とブランチを消す。消す前に、報告された HEAD が統合先に入り、統合先が push 済みであることを確かめる。squash で取り込んだブランチは `git branch --merged` では見分けられない。

## 収束しないとき

次のどれかが起きたら、同じ役に続けて頼まない。要件を読み直し、設計を見直す。

- 見込みを大きく超えた。
- 同じ指摘が、直しのあとも残った。
- 直しが、新しい不具合を持ち込んだ。

計測では、作る役を 3 体以上使った issue が、作業の時間の 1〜4 割を使っていた。継ぎ足しで合わせ続けるより、作り方を変えるほうが早い。
